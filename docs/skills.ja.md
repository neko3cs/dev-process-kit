# スキルリファレンス

[English](skills.md) | 日本語

dev-process-kit の3つのスキルが、何を読み、何を作り、何をしないかをまとめます。手順の詳細と判断基準は、各スキルの `SKILL.md` と `references/` 配下の参考資料が正本です。スキルのファイルは日本語で書かれていますが、作る Issue・設計文書・PR は対象リポジトリの言語に合わせます。

| スキル | 工程 | 読むもの | 作るもの |
| :--- | :--- | :--- | :--- |
| [`dev-process-kit:issue`](#dev-process-kitissue) | 起票 | 利用者の要望、Issue テンプレート | GitHub Issue、Issue コメント |
| [`dev-process-kit:design`](#dev-process-kitdesign) | 設計 | Issue、既存の設計文書、コード | 4つの設計文書、設計 PR、質問コメント |
| [`dev-process-kit:implement`](#dev-process-kitimplement) | 実装 | Issue、マージ済みの設計文書と設計 PR | プロダクトコード、テストコード、実装 PR |

どのスキルも、PR の書式・ブランチ名・テストフレームワーク・品質ゲートの方法は決めません。リポジトリの規約、テンプレート、利用者の指示に従います。

## `dev-process-kit:issue`

要望を GitHub Issue に起票します。正本: [`skills/issue/SKILL.md`](../plugins/dev-process-kit/skills/issue/SKILL.md)、テンプレートと `gh` 操作: [`references/templates-and-gh.md`](../plugins/dev-process-kit/skills/issue/references/templates-and-gh.md)

### 使う場面

- 機能要望やバグ報告を Issue にしたいとき
- 既存の Issue に、背景・調査結果・議論の経緯をコメントとして残したいとき

名前で呼んだときだけ動きます。「Issue を作って」のような一般的な依頼では起動しません。

```text
/dev-process-kit:issue ログイン画面がクラッシュする
```

### 動き

- 起票のたびに、対象リポジトリの `.github/ISSUE_TEMPLATE/` を読み直します。無ければ、所有者の `.github` リポジトリのテンプレートを使います。どちらにも無ければ、説明・動機と背景・受け入れ条件の見出しで書きます。`config.yml`・`config.yaml` はテンプレート選択画面の設定でテンプレートではないため、候補にしません。テンプレートがあれば、`blank_issues_enabled` の値に関わらず必ずどれかに従います。
- Issue Forms の `type: markdown` の要素は、GitHub の送信時と同じく本文に含めません。テンプレートのタイトルのプレフィックスとラベルに加え、`assignees`・`projects`・`type` も設定します。テンプレートのラベルが対象リポジトリに無ければ、ラベルは作りません。そのラベルを外して起票し、付けられなかったラベルを利用者に伝えます。
- 必須フィールドは必ず埋めます。本文は完成した要望として書きます。決まっていない部分は最も妥当な内容を選び、`仮定`・`TBD` などの印を付けずに要望として書きます。確認のために起票を止めず、その内容でよいかを Issue コメントで質問します。
- Issue は要件ごとに1つ起票します。依頼に、それぞれ単独で価値を届けられる要件が複数あれば、分け方（Issue ごとのタイトルと要件）を示し、別々の Issue に分けて起票してよいかを確認してから起票します。親子の Issue は使わず、一緒に起票したほかの Issue の番号を各 Issue にコメントします。
- 内容の精査で確かめられるチェック項目（「機密情報を含めていない」など）は、本文を精査してからチェックします。利用者本人の同意・確認を表す項目（行動規範への同意、重複を探したことなど）は、代わりにチェックしません。会話で同意・確認を明言していなければ、項目の文言を示して起票前に確認します。同意が得られなければチェックせず、必須の項目なら起票しません。
- 本文とコメントに書くのは、要望と、リポジトリに関する事実（コードの挙動、外部仕様、調査結果、選ばなかった案とその技術的な理由など）だけです。会話で聞いた利用者自身の事情（取引先や社名、別の案件、社内の予定、個人的な事情など）は、書くよう明示的に頼まれない限り書きません。動機に必要なら一般化して書きます。Issue はリポジトリを読める人すべてに見え、起票した時点で通知も届くため、後で消しても取り消せないためです。
- 起票の前に止まるのは、要件の分け方の確認、同意を表すチェック項目の確認、複数テンプレートから選び難いときの確認だけです。複数あっても1回の質問にまとめます。
- リポジトリの規約や利用者の指示で決まる言語で書きます。決まっていなければ、テンプレートの言語、リポジトリの主な文書の言語（訳ではなく正本の言語）、会話の言語の順で決めます。テンプレートの見出し・タイトルのプレフィックス・ラベルは訳さずにそのまま使います。
- 再現結果・環境・実測値などの事実は創作せず、未確認と書きます。
- 本文には要望を書き、長い調査結果や経緯はコメントに分けます。同じ話題のコメントは、足さずに書き換えます。書き換えるのはエージェントが書いたコメントだけで、他人のコメントや、同じアカウントで利用者が自分で書いたコメントは書き換えません。それらの内容が古くなったら、新しいコメントで補足します。

### しないこと

- 何を作るかの合意や、受け入れ基準の作り込み（`dev-process-kit:design` で行う）
- 起票に続けて設計・実装・PR 作成を始めること

## `dev-process-kit:design`

Issue を4つの設計文書に設計し、設計 PR を作ります。正本: [`skills/design/SKILL.md`](../plugins/dev-process-kit/skills/design/SKILL.md)、判断基準: [`references/policy.md`](../plugins/dev-process-kit/skills/design/references/policy.md)、PR 作成とブランチ取り込み: [`references/pr-and-sync.md`](../plugins/dev-process-kit/skills/design/references/pr-and-sync.md)

### 使う場面

- Issue を設計したいとき（`/dev-process-kit:design 12`、「#12 を設計して」）
- 設計 PR のレビュー指摘を反映したいとき
- 仕様変更を設計文書に反映したいとき

名前で呼んだときだけ動きます。「#12 を設計して」「ドキュメントを整備して」のような一般的な依頼では起動せず、`dev-process-kit:implement` からも呼ばれません。設計が足りないとき、`implement` は止まって、このスキルの実行を頼みます。

### 作る文書

| 文書 | 答える問い | 主な内容 |
| :--- | :--- | :--- |
| `requirements.md` | なぜ、誰のために、何を達成するか | 目的、利用者、利用シナリオ、業務要件、機能要件と受け入れ基準、非機能目標、対象外、用語 |
| `specification.md` | どの条件で、何が起きるべきか | 業務ルール（入力と期待結果の表）、画面操作、状態、データの意味と制約、入出力形式、エラー・通知 |
| `architecture.md` | どの構造・制約で実現するか、なぜか | 構成と依存、設計判断（ADR）、永続化・移行、共通実装規約、非機能の実現方式 |
| `tests.md` | 何をどこまで、どの環境・基準で検証するか | テストスコープ、テストレベルと使用ツール、テスト環境と外部境界、品質ゲートと基準、終了条件、重点リスクと検証限界 |

文書の置き場所は、既存の規約を優先します。指定がなければ既存の `docs/` の中、無ければリポジトリ直下に置きます。

### 動き

- 4つの文書が1つも無ければテンプレートから新しく作り、あれば該当する節だけを差分で更新します。既存の文書を丸ごと書き直すことはしません。一部の文書だけがあるときは、変更がその文書に当たる場合（テスト計画の変更なら `tests.md`）にだけ、無い文書をテンプレートから作ります。変更が当たらない文書は無いままにします。
- monorepo では、サービスごとに4文書の組を置けます。各組は、リポジトリ全体の組の `architecture.md` にある索引から探します。節ごとに更新できないほど大きくなった文書は、同じ名前のディレクトリに機能ごとに分け、元のファイルを索引として残せます。どちらの分け方も、構成だけを変える別の設計 PR で提案して行います。
- Issue が、それぞれ単独で価値を届けられる要件を複数含んでいれば、設計を始めずに止まります。分け方を示し、`/dev-process-kit:issue` で要件ごとに起票し直すよう頼みます。Issue の起票・編集・クローズは自分では行いません。
- 設計文書は完成品として書きます。決まっていない設計は最も妥当な案を選び、`仮定`・`未承認`・`TBD` などの印を付けずに、理由とともに仕様として書きます。選んだ案でよいかは設計 PR のコメントで質問し、回答は該当箇所の書き換えで反映します。
- 既存のコードから設計文書を新しく作るときも、文書には確認待ちの印を付けません。コードから読み取った現状の動作は、PR 本文と PR コメントで新しく選んだ案と区別して示し、仕様として追認するかを質問します。追認前の記述とコードの食い違いは、コードの不具合ではなく確認事項として扱います。設計 PR のマージ後に差異が見つかった場合は、Issue で報告してどちらに決めるかの判断を利用者に委ねます。
- 設計文書と設計 PR は、リポジトリの規約や利用者の指示で決まる言語で書きます。決まっていなければ、既存の設計文書の言語、リポジトリの主な文書の言語（訳ではなく正本の言語）、会話の言語の順で決めます。テンプレートは日本語で書かれています。別の言語では見出しと本文を訳し、節の構成・順序・見出しのレベルは変えません。既存の文書の見出しは訳し直さずに使います。未決の印は、どの言語でも書きません。
- コードと設計文書が食い違っていたら、文書を正とし、コードの不具合として報告します。食い違いは設計 PR の本文に一覧にし、PR のマージ後も追跡できるよう、`/dev-process-kit:issue` で Issue にするよう勧めます。
- 作業ブランチの作成・コミット・push・設計 PR の作成までを、操作ごとの許可を求めずに進めます。設計 PR は Issue を閉じないよう、`Refs #<番号>` だけの行で関連付けます。
- 並行する別の設計 PR が先に統合ブランチへマージされて衝突したときや最新へ追従させるときは、リポジトリの規約や利用者の指示に従って統合ブランチを取り込みます（指定が無ければマージ。rebase 後の push は `--force-with-lease` を使い、Ready for review の後の rebase と force push は規約や指示で求められない限り避けます）。マージ済みの合意内容を消さずに統合し、仕様どうしが矛盾する場合は PR を Draft にしたうえで PR 本文と PR コメントで確認を求めます。この PR で新しく追加した未マージの ADR 番号がマージ済みと重複していたら、マージ済みの番号を残して追加分だけを振り直し、PR 内の参照も合わせます。

### しないこと

- 実装（テストやプロダクトコードを書くこと）
- テストケース・テスト手順の文書化（テストコードを正とする）
- 実装タスク一覧（`tasks.md` など）の作成
- 現在のコード構造（関数の一覧や内部の呼び出し順序）の転記
- 設計 PR のマージ（人が判断する）

## `dev-process-kit:implement`

マージ済みの設計文書をもとに、Issue 1つにつき1つの実装 PR で実装します。正本: [`skills/implement/SKILL.md`](../plugins/dev-process-kit/skills/implement/SKILL.md)、PR とレビュー対応: [`references/pr-and-review.md`](../plugins/dev-process-kit/skills/implement/references/pr-and-review.md)、テストの定義: [`unit-test.md`](../plugins/dev-process-kit/skills/implement/references/unit-test.md)・[`integration-test.md`](../plugins/dev-process-kit/skills/implement/references/integration-test.md)・[`scenario-test.md`](../plugins/dev-process-kit/skills/implement/references/scenario-test.md)、品質ゲートと検証ガードレール: [`quality-gate.md`](../plugins/dev-process-kit/skills/implement/references/quality-gate.md)

### 使う場面

- 設計 PR がマージされた Issue を実装したいとき（`/dev-process-kit:implement 12`）
- 正しい動作がすでに設計文書に書かれているバグを直したいとき
- 実装 PR のレビュー指摘に対応したいとき

名前で呼んだときだけ動きます。「#12 を直して」のような一般的な依頼では起動しないため、このプロセスを使っていないリポジトリでプロセスを始めることはありません。

### 動き

- 設計文書の場所を、`design` が文書を置くときと同じ順（既存の規約、`docs/` の中、リポジトリ直下）で探します。設計文書があるかどうかと、PR が設計 PR かどうかは、この場所で判定します。
- Issue と、関連する設計 PR の差分を読み、設計文書と照らして作業範囲を決めます。
- 設計文書が無い、Issue の内容（バグ報告では、不具合そのものではなく Issue が期待する正しい動作）が設計文書に書かれていない、作業範囲に `TBD` が残っている、のどれかに当たれば実装を始めません。未マージの設計 PR のマージを待つか、何が足りないかを示して `/dev-process-kit:design` の実行を頼みます。設計文書は自分では書きません。
- 設計文書ごとに、次のレベルのテストを書きます。

  | 設計文書 | テスト |
  | :--- | :--- |
  | `requirements.md` の業務要件 | シナリオテスト |
  | `specification.md` | インテグレーションテスト（計算規則はユニットテストでもよい） |
  | 詳細設計（文書にしない） | ユニットテスト |

  `architecture.md` の制約は、ビルドの仕組みで強制するか、PR のレビューで照合します。
- 部品はユニットテストを先に書くテスト駆動開発（TDD）で作り、TODO リストの1項目ずつ Red → Green → Refactor を回します。
- 機能ができたらインテグレーションテストを書きます。仕様書から入力と期待結果を決め、システムの境界の内側ではテストダブルを使わずに結合して確かめます。境界の外は提供元のテスト環境を使い、テスト環境が無い場合はテストダブルで代替して未確認に書きます。テスト環境はあるが作業環境にその資格情報が無い場合は、テストダブルで代替して検証できる範囲を進め、確かめられなかった範囲と理由を PR 本文の未確認に書きます。外部サービスと接続したテストの要否は利用者が判断するため、`tests.md` や利用者の指示で方針が決まっていなければ PR コメントで要否を確認して Draft を維持し、方針が決まっていれば判断待ちにせず進めます。資格情報がある環境（CI のシークレットなど）でだけ実行する方針や検証の限界を残す必要があれば、PR コメントで `tests.md` への追記を提案します。
- 業務の流れが通るようになったらシナリオテストを書きます。業務要件の業務の手順をそのままテストの手順にし、GUI なら UI テスト、バッチならテスト用のスクリプトで確かめます。
- カバレッジはユニットテストとインテグレーションテストで測り、シナリオテストは含めません。
- テストは設計文書と同じ言葉で、仕様の文脈ごとにまとめ、期待結果まで含む名前を付けて、仕様として読めるように書きます。
- 業務ルールの表の行は、テストのデータとしてそのまま写します。
- 実装中に見つかった設計の問題を2つに分けます。設計文書に書かれた外部仕様（受け入れ基準、業務ルールの表、画面操作、入出力、`architecture.md` の制約）を変える必要がある場合や、書かれたとおりに作ると受け入れ基準を満たせない・文書どうしが矛盾する・データが消える場合は、実装を止めて実装 PR を Draft にし、`/dev-process-kit:design` の実行を頼みます。その設計 PR のマージを待ってから再開します。設計文書に書かれていない細部（内部設計）では止まらず、決めた内容をユニットテストで表し、PR 本文に挙げます。
- 実装中に利用者から仕様変更を求められたら、今の Issue は凍結した仕様のまま完了させ、変更を新しい Issue にするよう伝えます。
- 設計文書と食い違うコードは、Issue の作業範囲の中なら直します。作業範囲の外で見つけた食い違いは直さず、PR コメントと終わりの報告に一覧にし、実装 PR のマージ後も追跡できるよう、`/dev-process-kit:issue` で Issue にするよう勧めます。Issue は自分では起票しません。
- 設計文書に残したほうがよい情報は、そこには書かず、候補として PR コメントに残します。
- 同じ話題の PR コメントは、足さずに書き換えます。書き換えるのはエージェントが書いたコメントだけで、他人のコメントや、同じアカウントで利用者が自分で書いたコメントは書き換えず、新しいコメントで補足します。
- 実装 PR の本文には、作成時から `Closes #<番号>` だけの行を書きます。同じ Issue の設計 PR・実装 PR は、全文検索だけに頼らずこれらの行で探すため、番号に触れただけの PR を拾いません。受け入れ基準ごとの対応するテスト、確認済みと未確認の動作確認も書きます。
- 設計文書はどの言語で書かれていても読み、節は見出しの言葉ではなく役割で探します。決まっていない・承認されていないことを示す語や注記は、言語に関わらず未決の印として扱い（`仮定`・`TBD`・`Assumption`・`Unapproved` など）、実装を始めずに止まります。PR 本文とコメントは、リポジトリの規約や利用者の指示で決まる言語で書き、決まっていなければ設計文書と同じ言語で書きます。
- サービスごとの組や分割された文書があれば、索引をたどり、対象のサービスの組と、関係する子ファイルだけを読みます。
- 人の判断を待つ事項があれば Draft のままにし、PR コメントで質問します。`tests.md`・規約・指示で定めた品質ゲートと自動チェックへの対応を終えてから Ready for review にします。品質ゲートの実行では `references/quality-gate.md` のガードレールに従い、未実行や空の解析結果を合格にせず、基準の緩和や終了コードの隠蔽を避け、結果を確認済み・失敗/基準未達・対象外・未確認に分けて報告します。品質ゲートが定められていない場合は、既存のテスト・ビルド・型チェック・リンターのうちローカルで実行できるものを通し、実行したものと実行しなかったものを PR 本文の動作確認に分けて書き、必要なら `tests.md` に品質ゲートを定めることを PR コメントで提案します。
- Ready for review の後のレビュー対応は、ひとまとまりの対応ごとに1回だけ push します。
- 統合ブランチを実装ブランチに取り込む方法（マージか rebase か）は、リポジトリの規約や利用者の指示に従い、指定が無ければマージにします。rebase 後の push には `--force-with-lease` を使い、Ready for review の後の rebase と force push は規約や指示で求められない限り避けます。

### しないこと

- 設計文書に書かれていない仕様を、実装 PR の中で仮に決めて実装すること
- コードに合わせて設計文書を書き換えること
- 設計文書を書くことや、設計 PR を作ること（利用者が `dev-process-kit:design` を実行して行う）
- Issue への書き込み（Issue は読むだけ）
- 受け入れテストの GO / NO-GO の判断と、実装 PR のマージ（人が判断する）
