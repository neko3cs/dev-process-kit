# dev-process-kit の思想

[English](philosophy.md) | 日本語

dev-process-kit は、仕様駆動開発（SDD）だけでは扱いきれない範囲まで含めて、ソフトウェア開発プロセス全体を支援するために作りました。下敷きにしているのは、日本のソフトウェア開発で広く使われてきたウォーターフォール型の開発プロセスです。

## SDD より広い範囲を扱う

SDD は、仕様を先に書き、その仕様からコードを作ることに重心を置いています。実際の開発では、その前後にも工程があります。

- 仕様を書く前に、何が求められているのか（要件）をはっきりさせる
- 仕様を人が合意し、それ以降は勝手に変えない
- 実装中に仕様の問題が見つかったら、上流の工程に戻って直す
- 出来上がったものが業務で使えるかを、人が受け入れテストで判断する

dev-process-kit は、要件定義から受け入れテストまでをひと続きの工程として扱います。工程の区切りごとに人のレビューとマージを置き、AI が進める作業と人が判断する作業を分けます。

## ウォーターフォールの工程に沿って進める

工程は、上流から下流へ一方向に進みます。

| 工程 | 成果物 | スキル | 区切り |
| :--- | :--- | :--- | :--- |
| 要件定義 | Issue、要件定義書（`requirements.md`） | `dev-process-kit:issue`、`dev-process-kit:design` | — |
| 設計 | 仕様書（`specification.md`）、アーキテクチャ設計書（`architecture.md`） | `dev-process-kit:design` | 設計 PR のマージで仕様を凍結する |
| 実装とテスト | プロダクトコード、テストコード | `dev-process-kit:implement` | — |
| 受け入れテスト | GO / NO-GO の判断 | — （人が行う） | 実装 PR のマージで Issue が完了する |

### 要件定義は Issue から始める

開発の起点は Issue です。要望はすべて Issue として起票し、Issue で管理します。何を作るかが Issue に残っていれば、会話の履歴を持たない人や AI も後から同じところから始められます。

Issue に書くのは要望までです。要望がまだ固まっていない部分も、最も妥当な内容を選んで完成した要望として書き、Issue コメントで確認しながら先に進みます。何を作るかの合意と受け入れ基準は、要件定義書（`requirements.md`）にまとめます。要件定義書は仕様書・アーキテクチャ設計書と同じ設計 PR で作り、そのマージで一緒に合意します。

### 設計では、要件から「あるべき仕様」を決める

要件が固まってから設計に入ります。設計では、要件を満たすためにシステムやアプリがどう振る舞うべきかを定義し、次の3つの文書にまとめます。

| 文書 | 答える問い |
| :--- | :--- |
| 要件定義書（`requirements.md`） | なぜ、誰のために、何を達成するか |
| 仕様書（`specification.md`） | どの条件で、何が起きるべきか |
| アーキテクチャ設計書（`architecture.md`） | どの構造・制約で実現するか、なぜそうするか |

設計文書は、現在のコードを写したものではありません。人が決めた約束と、その判断の理由を残すものです。AI は設計文書を、仮定の並んだ下書きではなく完成品として書きます。決まっていない箇所は最も妥当な案を選んで仕様として書き、その案でよいかを設計 PR のコメントで人に問います。

3つの文書は、既定では1か所に1組だけ置きます。monorepo では、サービスごとに3文書の組を置けます。そのときは、リポジトリ全体の組の `architecture.md` に、ほかの組の索引を置きます。1つの文書が大きくなり、節ごとに更新できなくなったら、同じ名前のディレクトリに機能ごとに分け、元のファイルを索引として残せます。どちらの分け方も、仕様を変えずに構成だけを変える設計 PR で行います。

### 設計 PR のマージで仕様を凍結する

人が設計 PR をレビューしてマージすると、仕様が合意され、凍結されます。実装は、凍結された仕様だけをもとに行います。

コードと設計文書が食い違ったときは、設計文書を正とし、コードの不具合として扱います。利用者が確かめるのは文書で、コードではないからです。

### 仕様が変わったら、実装を止めて上流に戻る

実装の途中で仕様の不足や誤りが見つかっても、実装 PR の中で仮の仕様を決めて先に進むことはしません。実装を止めて利用者に知らせ、利用者が `dev-process-kit:design` で始める別の設計 PR で仕様を直します。その設計 PR がマージされ、仕様が凍結し直されてから実装に戻ります。

この手戻りは、ウォーターフォールで仕様変更を上流工程に差し戻すのと同じ考え方です。AI が実装の都合で仕様を書き換えたことにしないための決まりでもあります。

実装を止めるのは、外部仕様、つまり設計文書に書かれた内容が変わるときです。設計文書は外部設計までを書くので、文書に書かれていない細部（内部設計）は実装の中で決め、ユニットテストで表し、止まりません。細部のたびに止まると、手戻りが増えるだけだからです。

実装の途中で利用者が求めた仕様変更は、進めている Issue に混ぜません。その Issue は凍結した仕様のまま完了させ、変更は新しい Issue として設計・実装をやり直します。ウォーターフォールで、着手中の案件を終えてから仕様変更案件として取り組むのと同じです。ただし、書かれた仕様のままではデータが消えるなどの致命的な問題は、上と同じく実装を止めます。

### Issue 1つにつき、実装 PR は1つ

実装 PR は Issue 1つにつき1つ作ります。人の判断を待つ事項が残っているあいだは Draft のままにし、マージされる時点で Issue が完了している状態を保ちます。

1つの実装 PR ではレビューしにくい大きな Issue は、同じ Issue の PR を複数作るのではなく、子 Issue に分けます。設計は親の Issue のまま1つの設計 PR で行い、仕様の全体をまとめて合意・凍結します。分け方はその設計 PR が提案し、子 Issue はそれぞれ担当する受け入れ基準を受け持ちます。実装 PR は子 Issue ごとに1つ作り、すべての子がマージされたら親が完了します。

## テストはテストコードで定義する

テストケースやテスト手順は文書にせず、テストコードで定義します。テストの仕様をできるだけコードに落とし込んでおけば、変更のたびに同じテストを回帰テストとして流せます。

### テストの種類ごとに定義を決める

ユニットテスト・インテグレーションテスト・シナリオテストは、それぞれ何を確かめ、どう設計し、いつ書くかをこのプラグインが定めます。定義を決めておくのは、セッションごとに品質がばらつかないようにするためです。

| テスト | 呼び方 | 設計の方式 | 結合相手 | 書く時期 | カバレッジ |
| :--- | :--- | :--- | :--- | :--- | :--- |
| ユニットテスト | 単体テスト | ホワイトボックス | テストダブル（Mock・Stub）で切り離してよい | 実装より先（TDD） | 測る |
| インテグレーションテスト | 結合テスト | ブラックボックス。仕様書から入力と期待結果を決める | システムの境界の内側はテストダブルを使わず、本物を結合する | 基本は実装の後 | 測る |
| シナリオテスト | 総合テスト（システムテスト） | 業務要件で決めた業務の手順を、そのままテストの手順にする | 本物の構成で動かす | 基本は実装の後 | 測らない |

- **ユニットテストは実装より先に書く**: 詳細設計の代わりになるユニットテストを先に書けば、上流で決めたことから順に下流を作るという考え方が、詳細設計と実装のあいだでも守られます。TODO リストへの分解、Red → Green → Refactor のサイクル、テストを通す3つの戦略（仮実装・明白な実装・三角測量）まで、手順を定めています。
- **インテグレーションテストとシナリオテストは実装の後に書いてよい**: 期待結果は凍結された設計文書から決まっているので、実装の後に書いても、実装の動きに合わせたテストにはなりません。シナリオテストは業務の手順がそのままテストの手順になるので、業務要件が正しければ間違ったテストにはなりにくいです。
- **シナリオテストはカバレッジを測らない**: シナリオテストは業務要件のシナリオそのものです。コードカバレッジを上げるためにテストの手順を変えると、業務要件と突き合わせられなくなります。カバレッジは、ユニットテストとインテグレーションテストで測ります。

### 設計文書と検証の対応

どの設計文書をどのレベルのテストで確かめるかは、このプラグインが決めています。設計の段階ごとに、それを確かめる検証を対にして置く考え方です。

| 設計 | 検証 |
| :--- | :--- |
| 要件定義書の業務要件 | シナリオテスト（システムが担う部分）と受け入れテスト（人を含む業務全体） |
| 要件定義書の非機能要件 | 非機能要件の目標を合否条件とする検証 |
| 仕様書 | インテグレーションテスト |
| アーキテクチャ設計書 | 構造による強制とレビュー |
| 詳細設計（文書にしない） | ユニットテスト |

- 詳細設計は文書にしません。コードの写しになり、保守できなくなるためです。代わりに、ユニットテストを仕様として読めるように、実装より先に書きます。
- 仕様書の業務ルールは、入力と期待結果の表で書きます。テストはこの表の行をそのまま写して書くので、人は表とテストを見比べて確かめられます。
- 受け入れテストの実行や証拠集めは AI に任せられますが、GO / NO-GO は人が判断します。

## このプラグインが決めること、決めないこと

工程の流れと、その流れを守るための決まりは、このプラグインが決めます。利用者ごとに変えられる「やり方の好み」としては扱いません。

| このプラグインが決めること | リポジトリの規約と利用者の指示に任せること |
| :--- | :--- |
| 要望は Issue に起票する | Issue テンプレートの構成 |
| 設計は3つの設計文書にまとめる | 設計文書の置き場所（既存の規約があれば従う） |
| 設計 PR のマージで仕様を凍結する | PR の書式とテンプレート |
| Issue 1つにつき実装 PR は1つ | ブランチ名と作り方 |
| 判断待ちのあいだは Draft のままにする | コーディング規約 |
| 実装中に見つかった外部仕様の問題は、実装を止めて別の設計 PR で直す（内部設計はユニットテストで決める） | テストフレームワークやツール |
| 設計文書と検証レベルの対応 | 品質ゲートの方法 |
| テストの種類ごとの定義（ユニットテストの TDD を含む） | テスト名などの書き方の細かい規約 |
