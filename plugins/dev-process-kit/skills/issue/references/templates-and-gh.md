# 参考資料: テンプレートの扱いと `gh` 操作の詳細

`SKILL.md` の実行手順でテンプレートの読み取り・フィールド記入・`gh` コマンド実行・コメント書き換えを行うときに読む。

## 1. 書く言語の決定順

本文とコメントは、次の順で最初に決まった言語で書く（セッションごとに変えない）。

1. リポジトリの規約や利用者の指示（`AGENTS.md` など）で決まる言語
2. テンプレートがあれば、テンプレートの言語
3. README などリポジトリの主な文書の言語（言語ごとの版があれば訳ではなく正本の言語）
4. 利用者との会話の言語

テンプレートの見出し（`label`）・タイトルのプレフィックス・ラベルは、本文の言語に関わらず訳さずにそのまま使う（GitHub のフォームから送信したときと同じ本文にするため）。テンプレートが無いときの見出しは本文の言語に訳す。

## 2. テンプレートの探索と読み取り

テンプレートは更新される可能性があるため、作成のたびに読み直し、記憶から補わない。

1. 対象リポジトリの `.github/ISSUE_TEMPLATE/` にあるテンプレートを読む。
2. 無ければ、GitHub がテンプレートを引き継ぐ所有者の `.github` リポジトリの `.github/ISSUE_TEMPLATE/` を読む。

```bash
gh api repos/<owner>/<repo>/contents/.github/ISSUE_TEMPLATE --jq '.[].name'
gh api repos/<owner>/<repo>/contents/.github/ISSUE_TEMPLATE/<ファイル名> --jq '.content' | base64 -d
```

- 候補は `.md`・`.yml`・`.yaml` のうち `config.yml`（または `config.yaml`）を除いたものとする。`config.yml` はテンプレート選択画面の設定（`blank_issues_enabled`、`contact_links`）で、テンプレートではない。
- `blank_issues_enabled` の値に関わらず、テンプレートが1つでもあれば必ずどれかに従い、テンプレートを使わない空の Issue は作成しない。
- 複数あれば依頼の内容（バグ報告か機能要望かなど）に合うものを選ぶ。判断が難しい場合はユーザーに確認する。

### Issue Forms（YAML）から読み取る項目

- `title`: タイトルに付与するプレフィックス（例: `[Bug]: `）
- `labels`: 付与するラベル（例: `bug`、`enhancement`）
- `assignees` / `projects` / `type`: 起票時に設定する担当者・プロジェクト・Issue タイプ（フォーム送信時と同じ状態にするため、指定があればすべて設定する）
- `body`: 各フィールドの `type` / `id` / `label` / `required` / `placeholder`。`type: markdown` の要素はフォーム上の説明文で送信本文に出ないため含めない（見出しも作らない）

Markdown のテンプレートなら、その見出し構成とコメントの指示に従う。

## 3. 各フィールドの埋め方と本文の組み立て

- `required: true` のフィールドは必ず埋める。未決の要望や完了の目安は最も妥当な案を選んで完成した要望として書き、確認は起票後のコメントで行う。
- 任意フィールドは、書く内容がなければセクション自体を省略する（空見出しを作らない）。
- 受け入れ条件を書くフィールドがあれば、完了の目安をチェックボックスの箇条書きで簡潔に書く。入力と期待結果の表などの作り込みは設計文書で行うため求めない。「テストを書く」などプロダクトの振る舞いではない条件は書かない。
- `type: dropdown` は選択肢から該当するものを1つ選ぶ。未決の分類は最も妥当なものを選んで起票後に質問する。事実を表す項目で判断できない場合は、確認できていないことを本文に書き、確認済みの選択として扱わない。
- `type: checkboxes` は項目ごとに誰が確かめるものかで扱いを分ける。
  - **内容の精査で確かめられる項目**（機密情報を含めていないか等）: 本文を実際に精査したうえでチェックする。機械的にチェックしない。
  - **利用者本人の同意・確認を表す項目**（行動規範への同意、既存 Issue の重複確認、ライセンス同意等）: 本人が同意していないのに同意済みと記録しないため、エージェントが代わりにチェックしない。会話で本人が明言していればチェックし、そうでなければ起票前に項目の文言をそのまま示して確認する（重複確認では `gh issue list --search` の結果を添えてよいが、確認済みとする判断は本人に任せる）。
  - 同意・確認が得られなければチェックしない。その項目が `required: true` なら起票しない（フォームからも送信できないため）。どちらの場合もユーザーに伝える。
  - どちらに当たるか判断できない項目は、本人の同意・確認として扱う。

### 本文の形式

`gh issue create --template` は対話入力前提のため、GitHub Issue Forms が生成する `### {label}` の見出し形式を自分で組み立てて `--body-file` で渡す。順序は YAML の `body` に揃え、`type: markdown` は飛ばす。

```markdown
### 説明

...

### 再現手順

1. ...
2. ...
```

### テンプレートが無い場合の本文

テンプレートも利用者の指示も無ければ、次の見出しで書く（バグ報告なら再現手順・期待する動作・実際の動作を「説明」に含める）。

```markdown
### 説明

何が起きているか、何がほしいか。

### 動機・背景

なぜ必要か。誰が困っているか。

### 受け入れ条件

- [ ] 完了したと判断できるプロダクトの振る舞い
```

## 4. `gh issue create` の実行と属性の解決

```bash
gh issue create -R <owner>/<repo> \
  --title "[Bug]: ログイン画面でクラッシュする" \
  --body-file <一時ファイル> \
  --label bug
```

- 対象リポジトリは指定がなければ作業中のリポジトリ（`origin`）。別リポジトリ向けの場合は `-R owner/repo` を明示する。
- タイトルのプレフィックスとラベルは、テンプレートの `title` と `labels` をそのまま使う。テンプレートが無ければ付けない。
- **ラベルの事前照合**: `gh issue create` は対象リポジトリに無いラベルが1つでもあると失敗する（所有者の `.github` から引き継いだテンプレートで特に起こりやすい）。起票前に `gh label list -R <owner>/<repo> --limit 1000 --json name --jq '.[].name'` で存在を確認し、大文字・小文字を区別せずに照合する。無いラベルは `--label` から外して起票し、付けられなかったラベルをユーザーに伝える。ユーザーに頼まれない限りラベルは作成しない。
- **`assignees` / `type` / `projects`**: `assignees` は `--assignee`、`type` は `--type` で設定する。`projects` は `<owner>/<番号>` 形式で `--project` はタイトルを取るため、`gh project view <番号> --owner <owner> --json title --jq '.title'` でタイトルを調べて渡す。権限やトークンのスコープ不足で設定できなければ、その項目を外して起票し、設定できなかった項目と理由をユーザーに伝える。

## 5. 既存コメントの安全な書き換え

同じ話題の記録コメント（調査結果や論点の結論）を更新するときは、次を満たすコメントだけを `PATCH` で書き換える。

```bash
gh api -X PATCH repos/{owner}/{repo}/issues/comments/<コメントID> -f body=...
```

- `gh issue view <番号> --json comments` の `author.login` が `gh api user --jq .login` と一致し、かつ内容からエージェントが書いたと分かるものに限る。
- 他人のコメントや、同じアカウントでも利用者が自分で書いたコメント、判断できないコメントは書き換えない。
- 書き換えられないコメントの内容が古くなったら、どのコメントの何が変わったかを示す新規コメント（`gh issue comment <番号> -R <owner>/<repo> --body-file <一時ファイル>`）で補足する。
