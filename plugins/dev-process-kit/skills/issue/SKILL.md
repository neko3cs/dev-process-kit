# issue Skill

## 概要

GitHub Issueを `gh` コマンドで作成します。対象リポジトリにIssueテンプレートがあれば、そのいずれかに従います。テンプレートが無ければ、利用者の指示に従い、指示も無ければ下の「テンプレートが無い場合の本文」で書きます。

## Issue に残すもの

Issue は、ユーザーの要望を書く場所です。何を作るかの合意や受け入れ基準の作り込みは、設計文書で行うもので、このスキルの範囲外です。要望を聞く途中で分かったことは、後で設計や実装をする人が会話を持たずに読めるよう、Issue に書き残します。

| 残す先 | 残すもの |
| :--- | :--- |
| Issue 本文 | 要望。テンプレートのフィールドに書く |
| Issue コメント | 要望を聞く途中で生じた考え・暗黙知・調査結果のうち、本文に入れると長すぎるものや経緯（既存コードの挙動、外部仕様、選ばなかった案とその技術的な理由など） |

- 本文には合意の対象だけを置き、長い調査結果や経緯はコメントに分ける。
- 残すのは、次に読む人が会話を持たずに困るものに限る。作業の実況や、コードを読めば分かることは書かない。
- 本文にもコメントにも、書いてよいのは要望と、リポジトリに関する事実（コードの挙動、外部仕様、調査結果、選ばなかった案とその技術的な理由など）だけ。Issue はリポジトリを読める人すべてに見え、起票や投稿の時点で通知も届くため、後で消しても取り消せない。
- 利用者自身の事情は、会話で聞いても書かない。取引先や社名、別の案件・別のリポジトリの話、社内の予定や体制、個人的な事情などを指す。動機に必要なら、事情を外して一般化して書く（「A社の案件で、来月までに CSV 出力が必要」→「集計結果を CSV で受け渡したい」）。
- 利用者が、その事情を Issue に書くよう明示的に頼んだときだけ書く。
- 判断できないものは書かない。必要なら、起票後に利用者に足してもらえばよい。
- 同じ話題のコメント（ある調査の結果、ある論点の結論など）の内容が変わったら、新しいコメントを足さず、既存のコメントを書き換える（`gh api -X PATCH repos/{owner}/{repo}/issues/comments/<コメントID> -f body=...`）。古い内容が並ぶと、次に読む人が迷うため。ただし、人に判断を問うコメントは新しく書く（書き換えでは通知が飛ばないため）。

## 1つの Issue に1つの要件

Issue は要件の単位で起票します。1つの Issue が1つの要件だけを持てば、その Issue だけを読んで何の要件か分かり、設計PRと実装PRも Issue ごとに1つで済むためです。親子の Issue には分けません。子だけを読んでも、何の要件か分からなくなるためです。

- 依頼の中に、それぞれ単独で利用者に価値を届けられる要件が複数あるかを判断する。作業量やPRの大きさでは判断しない。
- 要件が1つなら、そのまま1つの Issue を起票する（確認しない）。
- 要件が複数なら、起票の前に分け方（Issue ごとのタイトルと要件）を示し、複数の Issue に分けて起票してよいかをユーザーに確認する。了承されたら、Issue ごとに手順1〜5を行う。1つにまとめるよう言われたら、1つの Issue で起票する。
- 分けて起票したら、各 Issue に、一緒に起票したほかの Issue の番号と、分けた理由をコメントで書く（手順5）。親子の紐づけ（`--parent`）は使わない。

## 起票前に確認する場合

このスキルは、確認なしで Issue を作成するのが原則です。未決の内容は最も妥当な内容を選んで書き、起票後に Issue コメントで確かめます。起票前に止まってユーザーに確認するのは、次の場合だけです。確認することがいくつあっても、1回の質問にまとめます。

| 場合 | 確認すること |
| :--- | :--- |
| 依頼に要件が複数ある | 要件ごとの分け方（「1つの Issue に1つの要件」） |
| 本人の同意・確認を表すチェック項目がある | その項目に同意・確認するか（手順2の `type: checkboxes`） |

## 実行手順

### 1. テンプレートを探す

対象リポジトリで使われるIssueテンプレートを、作成のたびに読み直す。テンプレートは更新される可能性があるため、フィールドの構成をこのスキルの記述や記憶から補わない。

- 対象リポジトリの `.github/ISSUE_TEMPLATE/` にあるテンプレートを読む。
- 無ければ、GitHub がテンプレートを引き継ぐ所有者の `.github` リポジトリの `.github/ISSUE_TEMPLATE/` を読む。

```bash
gh api repos/<owner>/<repo>/contents/.github/ISSUE_TEMPLATE --jq '.[].name'
gh api repos/<owner>/<repo>/contents/.github/ISSUE_TEMPLATE/<ファイル名> --jq '.content' | base64 -d
```

テンプレートの候補は、`.md`・`.yml`・`.yaml` のファイルのうち `config.yml`（または `config.yaml`）を除いたものとする。`config.yml` はテンプレート選択画面の設定（`blank_issues_enabled`、`contact_links`）で、テンプレートではない。`blank_issues_enabled` の値に関わらず、テンプレートが1つでもあれば必ずどれかに従う（「注意事項」）。

テンプレートが複数あれば、依頼の内容（バグ報告か機能要望かなど）に合うものを選ぶ。判断が難しい場合は、ユーザーにどれか確認する。

Issue Forms（YAML）のテンプレートからは、次を読み取る。

- `title`: タイトルに付与するプレフィックス（例: `[Bug]: `）
- `labels`: 付与するラベル（例: `bug`、`enhancement`）
- `assignees` / `projects` / `type`: 起票時に設定する担当者・プロジェクト・Issue タイプ。GitHub のフォームから送信したときと同じ状態にするため、指定があればすべて設定する（手順4）
- `body`: 各フィールドの `type` / `id` / `label` / `required` / `placeholder`。`type: markdown` の要素はフォームに表示される説明文で、送信しても本文に出ないため、本文に含めない（見出しも作らない）

Markdown のテンプレートなら、その見出しの構成とコメントの指示に従う。

### 2. 各フィールドの内容を埋める

本文とコメントは、次の順で最初に決まった言語で書く。セッションごとに決め方を変えない。

1. リポジトリの規約や利用者の指示（`AGENTS.md` など）で決まる言語
2. テンプレートがあれば、テンプレートの言語
3. README などリポジトリの主な文書の言語。言語ごとの版があれば、訳ではなく正本の言語
4. 利用者との会話の言語

テンプレートの見出し（`label`）・タイトルのプレフィックス・ラベルは、本文の言語に関わらず訳さずにそのまま使う。GitHub のフォームから送信したときと同じ本文にするため。テンプレートが無いときの見出し（「テンプレートが無い場合の本文」）は、本文の言語に訳す。

- 本文は、そのまま読める完成した要望として書く。`required: true` のフィールドは必ず内容を埋める。未決の要望や完了の目安は、会話・既存の仕様から最も妥当な内容を選び、要望として書く。`仮定`・`TBD` などの印や確認待ちの注記は付けず、確認のため起票前に止まらない（止まるのは「起票前に確認する場合」だけ）。選んだ内容でよいかは、起票後に Issue コメントで質問する（手順5）。
- 再現結果・環境・実測値などの事実は創作しない。確認できていない事実は、確認できていないとそのまま書く。
- 任意フィールドは、書く内容がなければそのセクション自体を省略する（空見出しを作らない）。
- `placeholder` は記入例（プレースホルダー）であり、そのまま転記しない。
- 受け入れ条件を書くフィールドがあれば、完了の目安をチェックボックスの箇条書きで簡潔に書く。入力と期待結果の表などの作り込みは、設計文書で行うため求めない。「テストを書く」など、プロダクトの振る舞いではない条件は書かない。
- `type: dropdown` は選択肢の中から該当するものを1つ選ぶ。未決の分類は最も妥当なものを選び、確認が必要なら手順5の質問に含める。事実を表す項目で判断できない場合は、確認できていないことを本文に書き、確認済みの選択として扱わない。
- `type: checkboxes` は、項目ごとに、誰が確かめるものかで扱いを分ける。
  - **内容の精査で確かめられる項目**（機密情報を含めていないか、など）: 本文を実際に精査したうえでチェックする。機密情報のチェックは注意事項の確認と直結するため、精査せずに機械的にチェックしない。
  - **利用者本人の同意・確認を表す項目**（行動規範への同意、既存の Issue を探して重複が無いことを確かめた、ライセンスへの同意など）: エージェントが代わりにチェックしない。チェックすると、本人が同意していないのに同意済みとして記録されるため。会話で本人がその項目に同意・確認したと明言していればチェックする。そうでなければ起票前に、項目の文言をそのまま示して確認する。重複の確認なら、`gh issue list --search` で探した結果も添えてよいが、確かめたとするのは本人に任せる。要件の分け方の確認があれば、同じ質問にまとめる。
  - 同意・確認が得られなければチェックしない。その項目が `required: true` なら起票しない（フォームからも送信できないため）。どちらの場合も、その旨をユーザーに伝える。
  - どちらに当たるか判断できない項目は、本人の同意・確認として扱う。

### 3. Issue本文を組み立てる

GitHub Issue Formsは送信時に各フィールドを `### {label}` の見出し＋内容に変換してIssue本文を生成する。`gh issue create --template` は対話入力前提のため、非対話で確実に全フィールドを反映させるには、この見出し形式の本文を自分で組み立て、`--body` / `--body-file` で渡す。

```markdown
### 説明

...

### 再現手順

1. ...
2. ...
```

フィールドの順序はYAMLの `body` の順序に揃える。`type: markdown` の要素は飛ばす。

#### テンプレートが無い場合の本文

テンプレートも利用者の指示も無ければ、次の見出しで書く。手順2の書き方（完成した要望として書く、事実を創作しない、受け入れ条件はチェックボックス）は同じように当てはめる。

```markdown
### 説明

何が起きているか、何がほしいか。

### 動機・背景

なぜ必要か。誰が困っているか。

### 受け入れ条件

- [ ] 完了したと判断できるプロダクトの振る舞い
```

バグ報告なら、再現手順・期待する動作・実際の動作を「説明」に含める。

### 4. `gh issue create` を実行する

```bash
gh issue create -R <owner>/<repo> \
  --title "[Bug]: ログイン画面でクラッシュする" \
  --body-file <一時ファイル> \
  --label bug
```

- 対象リポジトリは特に指定がなければ作業中のリポジトリ（`origin`）を使う。別リポジトリ向けの場合は `-R owner/repo` を明示する。
- タイトルのプレフィックスとラベルは、テンプレートの `title` と `labels` をそのまま使う。テンプレートが無ければ付けない。
- `gh issue create` は対象リポジトリに無いラベルが1つでもあると失敗する。所有者の `.github` リポジトリから引き継いだテンプレートでは特に起こりやすい。そのため、起票の前に `gh label list -R <owner>/<repo> --limit 1000 --json name --jq '.[].name'` で対象リポジトリのラベルを調べる。ラベル名は大文字・小文字を区別せずに照合する。無いラベルは `--label` から外して起票し、付けられなかったラベルをユーザーに伝える。ラベルを作るとリポジトリの設定が変わるので、ユーザーに頼まれない限り作らない。
- テンプレートに `assignees` があれば `--assignee`、`type` があれば `--type` で設定する。`projects` は `<owner>/<番号>` の形式で、`--project` はプロジェクトのタイトルを取るため、`gh project view <番号> --owner <owner> --json title --jq '.title'` でタイトルを調べて渡す。権限やトークンのスコープ不足で設定できなければ、その項目を外して起票し、設定できなかった項目と理由をユーザーに伝える（フォームから送信しても、書き込み権限の無い人には設定されない項目のため）。
- 本文は改行・見出しを含むため、シェルのクォート崩れを避けるためスクラッチディレクトリに一時ファイルを作成し `--body-file` で渡す。作成後は一時ファイルを削除する。
- 完成した要望として内容を揃え、このステップまで確認なしで進めて作成する（「起票前に確認する場合」を除く）。作成後にIssue URLを提示する。

### 5. 本文に入れなかったことと質問を Issue コメントに書く

起票までの会話で分かった調査結果や経緯のうち、本文に入れなかったもの（「Issue に残すもの」）があれば、作成した Issue にコメントとして書く。無ければ書かない。要件ごとに分けて起票した場合は、ほかの Issue の番号と分けた理由もここで書く。

手順2で未決の要望から選んだ内容があれば、その確認を新規コメントで質問する。対象のフィールド、本文に書いた内容、選んだ理由、代替案と違いを示し、「この内容でよいか、別案ならどれか」を答えられる形にする。人に判断を問うコメントなので、調査結果のコメントとは分けて新しく書く。回答で要望が変わったら、「起票後に分かったことを残す」に従って本文を書き換える。

```bash
gh issue comment <番号> -R <owner>/<repo> --body-file <一時ファイル>
```

## 起票後に分かったことを残す

このスキルだけの依頼では設計・実装やPR作成まで始めない。Issue は要望の記録で、何を作るかの合意は設計PRで行う。対応するPRができた段階で、未決事項への質問はIssueへの追加質問ではなく、そのPRに新規コメントで投稿する。

起票した後の議論で、考え・暗黙知・調査結果が生じたら、その Issue にコメントとして書く（手順5と同じ方法）。

- 議論の結果、要望が変わる場合は、本文も更新する（`gh issue edit <番号> --body-file <一時ファイル>`）。本文はテンプレートの見出し形式を保つ。
- 本文を更新したら、何をなぜ変えたかをコメントにも書く。本文には変更の経緯が残らないため。同じ論点の経緯を書いたコメントが既にあれば、そのコメントを書き換える（「Issue に残すもの」）。

## 注意事項

- テンプレートがあるリポジトリでは、テンプレートを使わない空のIssueを作成しない。
- テンプレートの構成は変更される可能性があるため、作成の都度手順1で最新の定義を読み、それに従う。
- ユーザー提供内容に個人情報・社外秘情報が含まれていないかを確認したうえで、本文とコメントに反映する（「Issue に残すもの」）。
