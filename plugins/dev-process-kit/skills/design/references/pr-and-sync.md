# 参考資料: 設計PRの作成と統合ブランチの取り込み

`SKILL.md` の「PRで確認する」や、並行する設計PRの取り込み・衝突解消を行うときに読む。

## 1. PR テンプレートの探索と適用

PR の起票方法と本文は、対象リポジトリの規約・指定された PR テンプレートに従う。テンプレートの指定が無ければ、作成・本文更新のたびに次の順で探して読み直し、構成を記憶から補わない。

1. 対象リポジトリの `.github/`・リポジトリ直下・`docs/` にある `pull_request_template.md`、または `.github/PULL_REQUEST_TEMPLATE/` の中のファイル
2. 対象リポジトリに無ければ、GitHub がテンプレートを引き継ぐ所有者の `.github` リポジトリの同じ場所（`gh api repos/<owner>/.github/contents/.github/pull_request_template.md --jq '.content' | base64 -d`）

`gh pr create` は非対話ではテンプレートを本文に当てないため、テンプレートの見出しとコメントの指示に従って本文を組み立て、`--body-file` で渡す。テンプレートのコメントは本文に残さない。

## 2. 設計PR 本文の必須項目

テンプレートや規約に関わらず、設計PR の本文には次の項目を必ず含める（レビューと、後で `dev-process-kit:implement` が作業範囲を読むのに使うため）。テンプレートに対応する節があればそこに書き、無ければ末尾に見出しを足す。テンプレートが無ければこの項目をそのまま見出しにし、本文の言語に訳す。

- **概要と関連Issue** — 何をなぜ設計したか、関連 Issue。設計だけで Issue は完了しないため `Closes #<番号>` ではなく `Refs #<番号>` とする。Issue 1つごとに `Refs #<番号>` だけの独立行を書き、文の中に埋め込まない（`dev-process-kit:implement` が同じ Issue の設計PRを探す目印にするため）。Issue が指定されていなければ確認のため止まらず番号なしで PR を作る。
- **変更した節** — 更新したファイルと節、変更しなかったファイルとその理由
- **食い違い** — 文書間・文書とコードの食い違いと、必要な判断。無ければ省く
- **確認したこと** — 確認したこと（ファイル間の整合、Issue との突き合わせなど）と、確認していないこと（確認できなかった事実、不足情報）を分けて書く。確認していないことを確認済みとして書かない。
- 各手順で PR 本文に書くよう求めたもの（配置先の判断理由、既存コードから読み取った記述の一覧、`AGENTS.md` への参照追加の提案、作り直す節の分類など）も該当するときは含める。

## 3. 選んだ案への質問と回答の反映

- 未決だった箇所で選んだ案や、既存コードから読み取った現状の動作を仕様として追認するかの確認は、本文の必須項目にせず、PR 作成・更新後に `gh pr comment <PR番号> --body-file <一時ファイル>` で別途投稿する（両者は区別して提示する）。
- 質問には、対象の節、文書に書いた案、理由、入力と期待結果の例、主要な代替案と影響を示し、「この案でよいか、別案ならどれか」を答えられる問いにする。既存の質問と回答を先に確認し、同じ質問を繰り返さず、新たな判断を求めるときだけ新規コメントを投稿する。
- 判断待ち・追認待ちがあっても PR 作成前に止まらず、回答が必要なら Draft PR にする。回答を反映して整合を確認するまで Draft を維持する。
- 回答で案が変わったら、文書の該当箇所を決まった内容に書き換え、回答の経緯を示す注記は足さない。既存文書に未決の印（言語不問）が残っていれば、同様に最も妥当な案で書き換えて印を外し PR コメントで質問する。

## 4. 統合ブランチの取り込みと衝突の解消

並行する別の設計PRが先に統合ブランチへマージされて衝突したときや、既存の設計ブランチを統合ブランチの最新へ追従させるときは、次の順で行う。

1. **統合ブランチを取り込む**: 取り込み方法（マージか rebase か）はリポジトリの規約や利用者の指示に従い、指定が無ければマージで取り込む。
   - rebase で push 済みの設計ブランチを更新するときは `--force` ではなく `git push --force-with-lease` を使う。リモートの更新と競合して拒否された場合は `--force` で上書きせず、リモートの変更を確認してから利用者に相談する。
   - Ready for review の後はレビュー中の差分やコメント追跡が壊れるため、rebase と force push は原則避ける。規約でマージコミットが禁止されているか利用者から rebase の指示がある場合だけ rebase して `--force-with-lease` で更新し、それ以外はマージにするか rebase してよいか利用者に確認する。
2. **設計文書の衝突を解消する**: 同じ節・表・一覧に別々の設計PRの変更が重なったときは、統合ブランチにマージ済みの合意内容を消さずに残し、両方が成り立つ形で統合する。
   - マージ済みの仕様・設計判断と今回の内容が両立しない（矛盾する）場合は、マージ済みの記述を黙って上書きしない。最も妥当な調整案で文書を完成品として整えたうえで PR を Draft に維持し（Ready なら Draft に戻す）、食い違いを PR 本文の「食い違い」に書き、PR コメントで調整案の可否を質問する。
3. **ADR 番号の重複を解消する**: テキスト上の衝突の有無に関わらず、この設計PRで `architecture.md` に追加した ADR が統合ブランチ側と重複していないか確認する。
   - 重複していれば、マージ済みの番号を残し、この PR で追加した ADR だけを統合ブランチの最大値の次へ振り直す（複数あれば連番）。
   - 振り直したときは、この PR の差分でその ADR を参照している箇所（旧 ADR からの相互参照、他の設計文書や節からの参照、PR 本文）も新しい番号に合わせる。
4. **整合を確認して更新する**: 4ファイル間（分割された子ファイルを含む）の整合を確認し、PR 本文（「変更した節」「食い違い」「確認したこと」）を最新の状態に更新して push する。
