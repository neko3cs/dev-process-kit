# 参考資料: 設計ドキュメント方針（判断基準の抜粋）

`SKILL.md` の手順で判断に迷ったときだけ読む。方針の全体像ではなく、判断に必要な部分だけを載せている。

設計文書は、マージすればそのまま合意済みの仕様になる完成品として書く。未決の設計は、表の期待結果も含めて最も妥当な案を選び、決まった仕様として書く。`仮定`・`未承認`・`仮案`・`TBD` などの未決の印は書かない。文書を書いた後、PRコメントで対象の節・案・理由・動作例・代替案と影響を示して確認し、回答で変わった内容は該当箇所を書き換えて反映する。実測値や過去の経緯など確認できない事実は創作せず、文書にも書かない。不足情報は PR本文に挙げ、PRコメントで質問する。

## 1. 「目的と成果 / 期待動作 / 実現方式と理由」の3段階

設計文書には、人が決めた約束と判断を残す。現在のコードの構造を写し続ける文書は作らない。

| ファイル | 答える問い | 残す情報 | 書かない情報 |
| :--- | :--- | :--- | :--- |
| `requirements.md` | なぜ、誰のために、何を達成するか | 課題、利用者、利用シナリオ、業務要件、機能要件、受け入れ基準、非機能目標、対象外、用語 | 詳細な入力・計算規則、画面操作、技術的な実現方式 |
| `specification.md` | どの条件で、何が起きるべきか | 業務ルール、画面と操作可否、実際の状態遷移、データの意味・関連・制約、入出力形式、互換性、失敗時の動作、エラー・通知 | 内部のクラス構成、関数の呼び出し順序、DBアクセス手順 |
| `architecture.md` | どの構造・制約で実現するか、なぜか | 全体構成、責務と依存、設計判断、永続化・整合性・移行、共通実装規約、非機能の実現方式、検証方針と重点リスク | 関数一覧、コードを逐次説明する処理図、テストケース一覧、進捗 |

要件と仕様は利用者と合意する業務の言葉で書く。ただし外部ファイル形式の項目名や型など、約束の特定に必要な技術情報は省かない。

## 2. 3文書の共通構成

| 文書 | 共通見出し |
| :--- | :--- |
| 要件 | 目的・背景／想定利用者／利用シナリオとシステムの範囲／業務要件／機能要件と受け入れ基準／非機能要件／スコープ外／用語集 |
| 仕様 | 機能一覧／業務ルール／画面・操作仕様／状態と遷移／データ定義／入出力・外部連携仕様／エラー・通知仕様 |
| アーキテクチャ | 全体構成と境界／責務と依存方向／設計判断と理由（ADR）／永続化・整合性・移行／共通実装規約／非機能の実現方式／検証方針と重点リスク |

各節の書くこと・書かないこと・確認する問いはテンプレートに示す。機能固有の小見出しはプロジェクトに合わせる。該当しない節は省略し、対象が無いこと自体が制約ならその理由を残す。既存文書を更新するときは、見出しの統一だけを目的に無関係な節を書き換えない。

`specification.md` は機能一覧を入口とし、業務ルール・画面・状態・データ・入出力を対応付ける。受け入れ基準から詳細規則を参照し、同じ規則の全文を複数箇所で維持しない。

## 3. 実装の説明と設計判断を分ける

現在のモジュール・クラス・関数の一覧、内部の呼び出し順序、詳細なデータアクセス手順が必要になったら、AI に現在のコードを読ませ、Markdown や HTML などで図示・説明させる。生成物は対象コミットと確認範囲を示す参考説明とし、保守対象の設計文書には加えない。コードだけから設計の理由を推測しない。

一方、責務の分担、依存方向、禁止する接続、保存・復旧の境界と、それらを選んだ理由は `architecture.md` に残す。機能固有でも複数箇所で守る判断は対象になる。コードの近くで完結する回避策と理由はコメントへ置けるが、既存の知識を移す場合は実際に保存されたことを確認してから文書側を整理する。

実装前の設計検討でも図を使える。確定した期待動作は仕様、構造上の制約と理由はアーキテクチャへ反映し、現在の実装図を常設の正本にしない。

## 4. 情報の性質による切り分け

**更新頻度や図の種類ではなく、何を決める情報かで分類する。** 頻繁に変わっても利用者との約束なら仕様である。混在する段落は分割する。

| 境界になる情報 | 分け方 |
| :--- | :--- |
| 受け入れ基準と詳細規則 | 要件に達成すべき成果、仕様に計算式・境界値・入力と結果。要件から詳細を参照する |
| 状態と業務の段階 | 操作や結果を制約する実際の状態は仕様。人とシステムで回すと合意した業務の流れは要件の業務要件。説明上の段階は要件の利用シナリオ。概念図から入力順の制約や編集ロックを推測しない |
| データモデルと保存方式 | 意味・関連・必須・既定値・区分は仕様。SQL物理型・テーブル構造・フレームワーク固有属性と理由はアーキテクチャ。外部形式の項目名・型は仕様 |
| 削除・更新・復旧 | 子も消える、既存メモを保つ、不正入力では何も変えない等は仕様。CASCADE、プレビュー中の変更禁止、トランザクション、移行手順と理由はアーキテクチャ |
| 入出力と互換性 | JSONスキーマ、ファイル名・日付・文字コード、旧形式の読み取り、欠損・破損時の結果は仕様。解析の責務・既定値へ復旧する方式・安全な移行の理由はアーキテクチャ。通信の有無で省略しない |
| 検証の観点 | 期待動作は仕様、検証方法・重点リスク・検証限界はアーキテクチャ、個別ケース・手順はテストコード。どの文書をどの検証で確かめるかは「設計文書と検証の対応」 |

既存資料を整理する場合は、記述ごとに移行先・重複統合先・保守しない理由を追跡する。設計理由、互換性、未検証の観点を「コードから分かる」として落とさない。記述の矛盾は PR本文で確認し、移行に紛れて仕様やプロダクトの動作を変更しない。

**ADR は決定の履歴を追記で残す。** 決定変更と書式統一を区別する。詳細は「ADR の記録と改定」に従う。

**二重管理を避ける。** 規則の正本を決め、他の節から参照する。コード・区分の定義はデータ定義の該当項目に含め、独立した一覧を重複作成しない。

**文書とコードが食い違ったら、文書を正とする。** 利用者は文書で確認し、コードはあまり読まない。文書に記載した仕様に合わせてコードを直し、コードに合わせて文書を書き換えない。合意済みの仕様を変更する提案は、文書を変更後の仕様に書き換えた設計PRとして出し、元の決定と変える理由を PR本文に示して PRコメントで確認する。ADR の決定を変える場合は「ADR の記録と改定」に従い、旧決定を保持する。

**設計文書は Issue・PR・コードから独立させる。** 必要な仕様と判断の理由は文書本文に残し、未実装でこれから実装が必要であることを示すメモは残さない。作業範囲・進捗は PR本文で管理する。設計が先行しているかは Issue・設計PRの差分とコードから確認し、確認できた未実装部分を不具合とは扱わない。

### ADR の記録と改定

`architecture.md` の「設計判断と理由（ADR）」に、次の6項目をこの名称・順序で記録する。

| 項目 | 見出し | 記載内容 |
| :--- | :--- | :--- |
| タイトル（Title） | レベル3: `ADR-001: タイトル` | 固定番号と決定を識別できるタイトル |
| ステータス（Status） | レベル4 | `Accepted` / `Proposed` / `Suspended` のいずれか |
| 意思決定内容（Decision） | レベル4 | 何を決めたか |
| 背景（Context） | レベル4 | 決定が必要になった背景 |
| 影響（Consequences） | レベル4 | 技術的負債、トレードオフ、維持・運用への影響 |
| 他に検討したもの（Alternatives Considered） | レベル4 | 比較した候補と選ばなかった理由 |

- 番号は `ADR-001` から始める。既存番号の最大値の次を採番し、欠番を詰めず、再採番・再利用しない。999を超えたら桁を増やす。
- Statusは実装状況と合意を確認して選ぶ。受け入れ済みは `Accepted`、提案・検討中は `Proposed`、保留・中断は `Suspended`。設計PRで追加する決定は、マージで合意されるものとして `Accepted` と書く。実装済みというだけで既存の決定を合意済みと扱わない。既存の決定で合意状況が確認できなければ、根拠から最も妥当な Status を選んで書き、PRコメントで確認する。
- 新たな決定には、今回の背景・見込む影響・比較案と選択理由を具体的に書く。過去の背景・比較履歴が不明な場合は創作せず、文書にも書かない。不足情報を PR本文に挙げ、PRコメントで質問する。「比較していない」と確認できた場合はその事実を書く。今回の比較は過去の比較履歴と区別する。
- 決定を変更する場合は新しい番号のADRを追記する。旧ADRに新ADRへの参照、新ADRに旧ADRへの参照を加え、旧決定とその理由は保持する。参照は該当見出しへのリンクか、固定番号で明示する。
- 既存ADRの書式統一を求められた場合は、既存番号と決定内容を保って該当箇所だけ整形する。番号が無い記録には未使用の次番号を付ける。不明な項目は創作しない。これは追記原則に対する書式だけの例外であり、決定内容やStatusを根拠なく変更する許可ではない。大きな構成変更は PRの差分で確認する。書式統一の中で決定内容は変えず、変えるべき決定は PRコメントで提案する。

## 5. テストの扱い

期待動作と検証方法を分ける。テスト専用の文書は原則作らない。

### 設計文書と検証の対応

設計の各段階に、それを確かめる検証を対にして置く。どの設計文書をどのレベルの検証で確かめるかは次の表に従う。各テストの定義（設計の方式、結合の範囲、書く時期、カバレッジ）と書き方は `dev-process-kit:implement` が定める。テストフレームワーク、ツール、構造で制約を強制する具体的な手段、ユニットテストの妥当性を確かめる具体的な手法は、プロジェクトの規約と利用者の指示に従う。

| 設計 | 検証 |
| :--- | :--- |
| `requirements.md` の業務要件（人とシステムを含む業務全体） | シナリオテスト（システムが担う部分）と受け入れテスト（人を含む業務全体） |
| `requirements.md` の非機能要件 | 非機能要件の目標を合否条件とする検証 |
| `specification.md` | インテグレーションテスト |
| `architecture.md` | 構造による強制とレビュー |
| 詳細設計（文書にしない） | ユニットテスト |
| ユニットテスト自体の妥当性 | レビューと、テストが仕様を押さえているかを確かめる手段 |

- **シナリオテスト**: 総合テスト（システムテスト）に当たる。機能をまたいで業務の流れを通し、業務要件のうちシステムが担う部分を確かめる。業務要件で決めた業務の手順がそのままテストの手順になるため、業務要件は手順として追える粒度で書く。カバレッジの測定には含めない（カバレッジのために手順を変えると、業務要件と突き合わせられなくなるため）。
- **インテグレーションテスト**: 結合テストに当たる。モジュールを結合し、1つの機能の振る舞いが仕様どおりかをブラックボックスで確かめる。システムの境界の内側ではテストダブルを使わない。ケースは仕様から決まるため、仕様は入力と期待結果が読み取れるように書く。UI を操作する場合もあり、シナリオテストとは粒度で区別する。業務ルールのうち、画面・保存・外部連携を介さずに入力から結果が決まる計算規則は、表の行に対応づけたユニットテストで確かめてもよい。
- **受け入れテスト**: 人の作業・判断を含む業務全体が回るかを確かめる。実行と証拠集め（操作ログ、スクリーンショット、録画）は AI に任せられるが、GO / NO-GO は人が判断する。リリース判定は検証対象の文書ではなく、受け入れテストの結果をもとに人が下す判断として扱う。
- **ユニットテスト**: 詳細設計は文書にせず（コードの写しになり保守できないため）、ユニットテストを仕様として読めるように、プロダクトコードより先に書いて、その代わりにする。
- **`architecture.md`**: 構造で強制できる制約は、モジュール・パッケージの分割などビルドの仕組みで、違反がビルドできないようにする。構造で強制できない制約は、PR レビュー（AI を含む）で `architecture.md` と照合する。どちらにもできない制約は書かない。
- **非機能要件**: 目標は `requirements.md` にあるため、検証も要件側で扱い、`architecture.md` の検証には含めない。目標を合否条件として確かめ、確かめられなかった目標は未確認として残す。実現方式とその限界は `architecture.md` の「非機能の実現方式」に書く。

検証できる仕組みがプロジェクトに無い場合（シナリオテストを実行する環境が無いなど）も、対の検証を黙って省かない。確かめられなかった範囲を未確認として PR に残し、仕組みが無いことと検証の限界を `architecture.md` の「検証方針と重点リスク」に書く。

### 置き場所

| 中身 | 置き場所 |
| :--- | :--- |
| 合意した業務の流れ（業務要件） | `requirements.md` の業務要件 |
| 合格基準（受け入れ基準） | `requirements.md` の機能要件と受け入れ基準 |
| 入力から結果が決まる規則（業務ルール） | `specification.md` の業務ルールに入力と期待結果の表で |
| テスト方針、重点リスク、検証限界、使用ツール、カバレッジ基準（ユニットテストとインテグレーションテストで測る）、テストダブルで置き換えた外部とその理由、CI での実行 | `architecture.md` の検証方針と重点リスク |
| 機能ごとのテスト観点 | 期待動作は仕様、検証方法・重点リスクはアーキテクチャに分ける |
| テストケース・手順 | **テストコード**（文書化しない） |
| 体制・スケジュール | 設計ドキュメントの範囲外 |

**業務ルールの表はテストケースではない。** どの入力でどの結果になるかという仕様（顧客と合意する規則）であり、テストの手順やデータの網羅ではない。テストはこの表の行を写して書く。

**テストケースそのものは規模にかかわらず文書に書かない。** ケースと手順はテストコードを正とする。ただし、実行可能であることは期待値の正しさや網羅性の証明ではない。既存の観点を整理する際は、テストへの反映を未確認のまま削除しない。期待動作とリスクを残し、実際に検証できた範囲と未確認を区別する。

例外的に `test-strategy.md` を切り出すのは、テスト方針の記述量が増えて `architecture.md` を圧迫し始めたとき、または複数ベンダーでの分担・外部委託・監査対応・契約上の納品物が絡むとき。個人開発・小規模開発では該当しない。

## 6. 図の使い分け

図が表す約束・判断で配置先を決める。同じ種類の図でも、現在の実装を写す説明は保守対象外になる。

| ファイル | 設計項目 | 図 |
| :--- | :--- | :--- |
| `requirements.md` | システムの範囲・利用シナリオ・業務要件 | ユースケース図、業務フロー |
| `specification.md` | 操作可否を定める状態・画面遷移 | ステートマシン図、画面遷移図 |
| `specification.md` | データの意味・関連 | ER 図、概念的なクラス図 |
| `specification.md` | 入出力の約束 | シーケンス図 |
| `architecture.md` | システム構成・配置・責務・依存 | 配置図、コンポーネント図、パッケージ図 |
| コードから必要時に生成 | 現在のクラス構成・内部呼び出し | クラス図、シーケンス図など |

**図を描かない領域を押さえておく。** 非機能要件、CRUD、メッセージ定義、ADR、共通規約はすべて表かテキストが最適で、UML の出番がない。設計ドキュメントのかなりの部分は UML の外側にある。

**運用方針**

- 5つの図（クラス図・ユースケース図・アクティビティ図・ステートマシン図・シーケンス図）を毎回フルで描かない。案件ごとに濃淡をつける
- その設計で **一番リスクや迷いがある観点** を選んで描く。状態が複雑ならステートマシン図を厚めに
- 図は約束や判断を伝える粒度に留め、関数シグネチャや内部呼び出しの一覧を転記しない
- コミュニケーション図・相互作用概要図は不要（シーケンス図／アクティビティ図と情報量が同じ）
