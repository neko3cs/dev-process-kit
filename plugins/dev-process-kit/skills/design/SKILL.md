# design Skill

`requirements.md` / `specification.md` / `architecture.md` / `tests.md` の4ファイルを作成・更新します。

| ファイル | 答える問い | 残す情報 |
| :--- | :--- | :--- |
| `requirements.md` | なぜ、誰のために、何を達成するか | 目的、利用者、利用シナリオ、業務要件、機能要件と受け入れ基準、非機能目標、対象外、用語 |
| `specification.md` | どの条件で、何が起きるべきか | 業務ルール、画面操作、状態、データの意味と制約、入出力形式、互換性、エラー・通知 |
| `architecture.md` | どの構造・制約で実現するか、なぜか | 構成と依存、設計判断、永続化・整合性・移行、共通実装規約、非機能の実現方式 |
| `tests.md` | 何をどこまで、どの環境・基準で検証するか | テストスコープ、テストレベルと使用ツール、テスト環境と外部境界、品質ゲートと基準、終了条件、重点リスクと検証限界 |

記載基準・切り分け・テストと図・分割方針は [方針の抜粋](references/policy.md) を、各節の構成は [テンプレート](assets/templates/) を参照します。各文書は [設計文書と検証の対応](references/policy.md#設計文書と検証の対応) で確かめられるように書きます。

## 責務と原則

- **責務の境界**: 設計文書4ファイルの作成・更新と設計PRの作成・更新だけを行う（テスト・プロダクトコードの実装や Issue への書き込み・起票・編集・クローズはしない）。文書とコードが食い違ったら文書を正としてコードの不具合を報告する（利用者が確認するのは文書のため）。
- **読者向けの完成品として書く**: 設計PRのマージで文書に書いた内容がすべて合意・凍結されるため、そのままマージできる状態で書く。
  - Issue の本文・コメントで決まった内容を引き継ぐ（Issue コメントで未回答の内容は合意済みと扱わず設計で決める）。
  - 未決の設計は会話・既存仕様・コード・一般的な利用例から最も妥当な案を選び、表の期待結果も含めて決まった仕様として書く。未決の印やテンプレートの案内・未使用要素は残さない（例: `TBD`・`仮定`・`未承認`・`Assumption`・`現状（コードから読み取り）`・`<!-- -->`・空見出し・空 Mermaid・仮 ADR・回答経緯の注記）。選んだ案の確認や既存コード読み取りの追認は PR コメントで行う。
  - 確認できない実測値や過去の経緯などの事実は創作せず、不足情報は PR 本文の「確認したこと」と PR コメントに挙げる。
- **Issue・PR・コードから独立させる**: 要望・判断理由・受け入れ基準は文書本文に残し、未実装メモ・実装タスク一覧（`tasks.md`）・テストケース手順・現在の実装構造の写し（関数シグネチャや内部処理）は書かない（進捗は Issue/PR、ケースはテストコードが正本のため）。守るべき責務・制約と理由は残す。

## Issue から設計する

Issue 番号を渡されたら、`gh issue view <番号> --comments` で本文とコメントを読みます。設計PRへのレビュー指摘も更新モードで設計文書を直します。

- **要件を複数含む Issue は止まる**: Issue は1つにつき1つの要件（設計PR・実装PRも1つ）です。単独で利用者に価値を届けられる要件が複数あれば（作業量や PR の大きさでは判断しない）、設計を始めずに止まり、要件ごとの分け方（タイトルと要件）を示して `/dev-process-kit:issue` で起票し直すよう利用者に頼んで終える。設計PR・ブランチは作らず、Issue も起票・編集・クローズしない。親子 Issue には分けない。
- **設計文書への落とし込み**:
  - 受け入れ基準は `requirements.md` の「機能要件と受け入れ基準」に業務の言葉で併記する（人の作業・判断を含む業務の流れが変わるなら「業務要件」も更新）。
  - 計算・変換・入力チェックなど入力から結果が決まる規則は、`specification.md` の「業務ルール」に入力と期待結果の表で書く（表は規則でありテストケースではない）。
  - 選んだ案の理由は判断理由として文書に残し、書き終えたら「PRで確認する」に進む（会話で事前確認を求めて止まらない）。

## 書く言語

設計文書・設計PRの本文とコメントは、次の順で最初に決まった言語で書きます（セッションごとに変えない）。

1. リポジトリの規約や利用者の指示（`AGENTS.md` など）で決まる言語
2. 既存の設計文書の言語
3. README などリポジトリの主な文書の言語（言語ごとの版があれば訳ではなく正本の言語）
4. 利用者との会話の言語

日本語以外で書くときは、テンプレートの見出しと本文を訳す（節の構成・順序・見出しレベルは変えない）。既存の設計文書がある場合はその見出しをそのまま使い訳し直さない。このスキルが挙げる節名や PR 本文の必須見出しは、訳した文書では対応する見出しを指す。

## モード判定と手順

まず対象の設計文書を特定します。サービスごとのセットやファイル分割があれば（[設計文書の分割](references/policy.md#7-設計文書の分割)）、ルートセットの `architecture.md`「全体構成と境界」や索引から対象だけを選びます。対象ディレクトリの4ファイルの有無でモードを決めます（0件 → 新規作成、1件以上 → 更新で既存は上書きしない）。一部だけある場合も更新モードで進め、無いファイルは変更が当たるときだけ作ります。

### 新規作成モード

1. 配置先はリポジトリ直下の `docs/` に固定する（無ければ作る。リポジトリの規約が別の場所を指していても変えない）。monorepo の新サービスはそのサービスのディレクトリの `docs/` に置き、ルートセットの索引にも足す。
2. `assets/templates/` の4ファイルを配置先へコピーし、必要なら訳す。
3. リポジトリの内容（README、コード、`AGENTS.md`、Issue、説明）から確認できた事実と、未決箇所で選んだ案を、どちらも決まった設計として各節に書く。
4. 既存コードから読み取った現状の動作がある場合は、まだ仕様として合意されていないため、該当する節を PR 本文にまとめ、PR コメントで「読み取りが現状と合っているか、この現状を仕様として追認してよいか」を選んだ案の質問と分けて確認し、追認待ちのあいだ PR を Draft に維持する（詳細: [方針の抜粋](references/policy.md#4-情報の性質による切り分け)）。
5. 完成品として不要な要素を整理する。案件に無い節は省略する（外部通信がなくてもファイル入出力は「入出力・外部連携仕様」に書き、対象が無いこと自体が制約なら理由を残す）。HTML コメント、空の Mermaid ブロック、記録する決定が無い ADR ひな型（0件なら節も省略）、空見出しはすべて削除する。
6. `AGENTS.md` に `architecture.md` への参照が無ければ PR 本文で追加を提案し（`AGENTS.md` 自体は変更しない）、「PRで確認する」に進む。

### 更新モード

1. ユーザーの説明、`git diff`、Issue、直前の実装から何が変わったかを掴む。
2. 下のルーティング表で**更新すべきファイルだけ**を選ぶ（分割文書は対象の子ファイルのみ）。選んだファイルが無ければ `assets/templates/` から作って該当節だけを書き、他の節は新規作成モードの手順5と同じく整理する。選ばれなかった無いファイルは作らない（4文書をそろえるだけの追加は仕様の変更ではないため）。更新のたびに無関係な節を読む必要が出てきたら、構成だけを変える別の設計PRでの分割を PR 本文で提案する。
3. 該当ファイルの該当節だけを差分更新する（全文書き直しはしない。大きく作り直す場合も節ごとの分類と理由を PR 本文に示して差分で提出し、対象外の既存資料は触らない）。
4. 変更後、ファイル間およびコードとの整合を確認する。
   - `specification.md` の機能が `requirements.md` に無い → 要件の追加漏れ
   - `specification.md` と `architecture.md` が両立しない → 食い違いと必要な判断を PR 本文に記録
   - コードと文書が食い違う → **文書を正とし、コードの不具合として報告する**（コードは直さない）。食い違った箇所（文書の節、コードの場所）と文書の記述を一覧にして PR 本文の「食い違い」と終わりの報告に示す。Issue は起票せず、終わりの報告で食い違いを Issue にするかを利用者に確認する（勧めるだけで終えない。起票する場合は利用者が `/dev-process-kit:issue` を呼び、それが起票の承認になる）。ただし、設計が先行していると確認できる箇所、または新規作成の未マージ PR で未追認の箇所（[方針の抜粋](references/policy.md#4-情報の性質による切り分け)）はコードの不具合としない。仕様変更として文書更新を依頼された場合は依頼どおり文書を直す。
5. 更新した節と変更しなかったファイルの理由を PR 本文に書き、「PRで確認する」に進む。

### ルーティング表

| 変わったもの | 更新するファイル |
| :--- | :--- |
| 目的、利用者、利用シナリオ、業務要件、機能要件、受け入れ基準、非機能目標、スコープ、用語 | `requirements.md` |
| 入力と結果、計算・検証規則、画面と操作可否、実際の状態遷移、データの意味・関連・制約、入出力形式、互換性、エラー・通知 | `specification.md` |
| 全体構成と境界、不変条件、責務と依存、技術選定、設計理由（ADR）、永続化・整合性・移行、共通実装規約、非機能の実現方式 | `architecture.md` |
| テストスコープ、テストレベルと使用ツール、テスト環境と外部境界、品質ゲートと基準、終了条件、重点リスクと検証限界 | `tests.md` |
| 現在のクラス・関数一覧、内部呼び出し順序、詳細なデータアクセス手順 | 保守対象外（必要時に現在のコードから説明） |

迷ったら**達成目標・期待動作・実現方式・検証計画のどれか**で分けます（境界例: [情報の性質による切り分け](references/policy.md#4-情報の性質による切り分け)）。ADR は追記で履歴を残し、決定変更は新番号を追加して相互参照します（書式・Status・例外: [ADR の記録と改定](references/policy.md#adr-の記録と改定)）。

## PRで確認する

依頼には作業ブランチ作成・コミット・push・PR 作成/本文更新・未決事項への質問コメント投稿までを含みます。操作ごとの許可や事前承認を会話で求めず、レビューできる PR にして URL を提示します（マージはユーザーの判断）。

- 既存の設計ブランチや PR があれば再利用し、今回の対象変更だけをコミットする。実装の途中で設計変更が必要になった場合も、統合ブランチから切った設計用ブランチで設計文書だけの設計PRにする（実装ブランチには含めない）。
- PR テンプレート探索、必須項目（`Refs #<番号>` 独立行など）、選んだ案への質問コメント、統合ブランチの取り込みと衝突・ADR 番号重複の解消は [PR 作成と統合ブランチ取り込み](references/pr-and-sync.md) に従う。
