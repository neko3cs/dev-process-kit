# design Skill

`requirements.md` / `specification.md` / `architecture.md` の3ファイルを作成・更新します。

| ファイル | 答える問い | 残す情報 |
| :--- | :--- | :--- |
| `requirements.md` | なぜ、誰のために、何を達成するか | 目的、利用者、利用シナリオ、業務要件、機能要件と受け入れ基準、非機能目標、対象外、用語 |
| `specification.md` | どの条件で、何が起きるべきか | 業務ルール、画面操作、状態、データの意味と制約、入出力形式、互換性、エラー・通知 |
| `architecture.md` | どの構造・制約で実現するか、なぜか | 構成と依存、設計判断、永続化・整合性・移行、共通実装規約、非機能の実現方式、検証方針と重点リスク |

各ファイルの記載基準、情報の性質による切り分け、テストと図の扱いは [方針の抜粋](references/policy.md) を読んでください。どの設計文書をどのレベルの検証で確かめるかは [設計文書と検証の対応](references/policy.md#設計文書と検証の対応) に従い、各文書はその検証で確かめられるように書きます。各節に書くこと・書かないこと・確認する問いは [テンプレート](assets/templates/) にあります。

設計文書は、そのままマージできる完成品として書きます。設計PRのマージで、文書に書いた内容がすべて合意されるためです。

- Issue の本文・コメントで決まった内容を引き継ぎます。Issue コメントで確認を求めたまま回答の無い内容は合意済みと扱わず、設計で決める対象にします。
- 未決の設計は、会話・既存仕様・コード・一般的な利用例から最も妥当な案を選び、決まった仕様として該当箇所に書きます。表の期待結果も具体的に埋めます。
- `仮定`・`未承認`・`仮案`・`TBD` などの未決の印や、確認待ちを示す注記は文書に書きません。選んだ案の確認は PRコメントで質問し、回答で変わった内容は該当箇所を書き換えて反映します。
- 確認できない実測値や過去の決定理由などの事実は創作せず、文書にも書きません。不足情報は PR本文の「確認したこと」に挙げ、PRコメントで質問します。

## Issue から設計する

Issue 番号を渡されたら、その Issue を設計文書に落とし込みます。Issue は要望を書く場所で、何を作るかの合意と受け入れ基準の正本は設計文書です。

1. `gh issue view <番号> --comments` で本文とコメントを読む。Issue が要件を複数含んでいれば、ここで止まる（「要件を複数含む Issue」）。そうでなければ、その内容を「変わったもの」として下の判定と手順に進む。設計文書が無いリポジトリでは、新規作成モードで3ファイルを作る。Issue には書かない。
2. 受け入れ基準は、`requirements.md` の「機能要件と受け入れ基準」に、業務の言葉の文章で併記する。人の作業・判断を含む業務の流れが変わるなら、`requirements.md` の「業務要件」も更新する。
3. 計算・変換・入力チェックなど、入力から結果が決まる規則は、`specification.md` の「業務ルール」に入力と期待結果の表で書く。表にするのは規則で、テストケースではない（[テストの扱い](references/policy.md#5-テストの扱い)）。
4. 未決の箇所は最も妥当な案を選び、表の期待結果も含めて決まった仕様として書く。選んだ理由は、判断の理由として文書に残す。
5. 設計文書は Issue・PR・コードから独立して仕様を理解できるように、要望の内容・判断の理由・受け入れ基準を本文に記載する。未実装でこれから実装が必要であることを示すメモは残さない。作業範囲や進捗は PR本文に残す。
6. 書き終えたら、変えた節と未確認事項を PR本文に書き、「PRで確認する」に進む。選んだ案の確認は PRコメントで質問する。会話で確認を求めて止まらない。

設計PRへのレビュー指摘も、更新モードで設計文書を直します。

### 要件を複数含む Issue

Issue は1つにつき1つの要件で、設計PRと実装PRも Issue ごとに1つです。それぞれ単独で利用者に価値を届けられる要件を1つの Issue が複数含んでいれば、設計を始めずに止まります。作業量やPRの大きさでは判断しません。

- 要件ごとの分け方（Issue ごとのタイトルと要件）を示し、`/dev-process-kit:issue` で要件ごとの Issue を起票し直すよう利用者に頼んで終える。設計PRもブランチも作らない。
- Issue を起票・編集・クローズしない。元の Issue をどうするか（閉じる、1つの要件に書き換える）は利用者に任せる。
- 親子の Issue には分けない。子だけを読んでも、何の要件か分からなくなるため。

## 書く言語

設計文書、設計PRの本文とコメントは、次の順で最初に決まった言語で書きます。セッションごとに決め方を変えません。

1. リポジトリの規約や利用者の指示（`AGENTS.md` など）で決まる言語
2. 既存の設計文書の言語
3. README などリポジトリの主な文書の言語。言語ごとの版があれば、訳ではなく正本の言語
4. 利用者との会話の言語

テンプレートは日本語で書かれています。別の言語で書くときは、テンプレートの見出しと本文をその言語に訳して使います。

- 訳すのは言葉だけで、節の構成・順序・見出しのレベルは変えない。
- 既存の設計文書があれば、その見出しをそのまま使い、訳し直さない。見出しが変わると、更新や `dev-process-kit:implement` が同じ節を見つけにくくなるため。
- このスキルが挙げる節の名前（「機能要件と受け入れ基準」「業務ルール」など）は、訳した文書では対応する節を指す。設計PRの本文の必須項目（「PRで確認する」）の見出しも、本文の言語に訳す。

## 最初に判定する

まず、対象の設計文書を決めます。サービスごとのセットやファイルの分割があれば（[設計文書の分割](references/policy.md#7-設計文書の分割)）、ルートのセットの `architecture.md` の「全体構成と境界」にある索引から、変更の対象のセットを選びます。分割された文書は、索引の文書から対象の子ファイルだけを選びます。

対象ディレクトリに3ファイルが存在するか調べ、モードを決めます。

- 1つも無い → **新規作成モード**
- 1つ以上ある → **更新モード**（既存ファイルは絶対に上書きしない）
- 一部だけある → 無いファイルは新規作成モード、あるファイルは更新モード

## 手順: 新規作成モード

1. 配置先を確認する。既存の配置規約を優先し、指定がなければ既存の `docs/` 配下、無ければリポジトリ直下に置く。判断の理由は PR本文に記載する。monorepo で新しいサービスのセットを作るときは、[設計文書の分割](references/policy.md#7-設計文書の分割) に従い、ルートのセットの索引にも足す。
2. `assets/templates/` の3ファイルを配置先へコピーする。日本語以外で書くときは、見出しと本文を訳す（「書く言語」）。
3. リポジトリの内容（README、コード、`AGENTS.md`、Issue、ユーザーの説明）から確認できた事実と、未決の箇所で選んだ案を、どちらも決まった設計として各節に書く（`現状（コードから読み取り）` のような確認待ちの印や注記は文書に書かない）。Issue 番号を渡された場合は、「Issue から設計する」の手順2〜5も当てはめる。
4. 選んだ案には具体的な期待動作・理由を記載し、実装に移れる設計にする。既存のコードから読み取った現状の動作がある場合は、人がまだ仕様として合意したものではないため、「新しく選んだ案」や「Issue・ユーザーの説明で決まった内容」と区別して、どの節がコードの読み取りに基づくかを PR本文にまとめる。PRコメントでは「読み取りが現状と合っているか、この現状を仕様として追認してよいか」を確認し、選んだ案への質問と分けて提示する。追認や回答を待つあいだは PR を Draft に維持する。未確認事項は PR本文に書き、選んだ案の確認は PRコメントで質問する。
5. その案件に無い節は省略する。外部通信がなくてもファイル入出力は「入出力・外部連携仕様」に書く。対象が無いこと自体が制約なら、その理由を関係する節に残し、記載漏れと区別する。空の見出しを残さない。
6. Mermaid の空ブロックは、実際に図を描く箇所だけ埋める。埋めない空ブロックは削除する。
7. ADR のひな型（`### ADR-001: タイトル` と、その下の5項目の見出し・案内・`Accepted`）は、記録する決定ごとに複製して埋める。記録する決定が無ければ、ひな型を丸ごと削除する。番号・タイトルが仮のままの ADR を残さない。ADR が1件も無ければ、手順5に従って「設計判断と理由（ADR）」の節も省略する。
8. テンプレートの HTML コメント（`<!-- -->` で書かれた「書く / 書かない / 確認」などの案内）は、各節を書き終えたらすべて削除する。案内は書き手への指示で、文書の読者には要らず、書き手はいつでもテンプレートで読めるため。
9. `AGENTS.md` に `architecture.md` への参照が無ければ、実際の配置先への参照追加を PR本文で提案する。今回の設計文書作成に付随して `AGENTS.md` は変更せず、「PRで確認する」に進む。

## 手順: 更新モード

1. 何が変わったかを掴む。ユーザーの説明、`git diff`、Issue、直前の実装内容を材料にする。
2. 下のルーティング表で**更新すべきファイルだけ**を選ぶ。無関係なファイルは開かない。分割された文書は、索引から該当する子ファイルだけを開く。更新のたびに無関係な節まで読む必要が出てきたら、[設計文書の分割](references/policy.md#7-設計文書の分割) に従って分けることを PR本文で提案する。分割は構成だけを変える別の設計PRで行い、今回の仕様の変更と同じPRに含めない。
3. 該当ファイルの該当節だけを差分更新する。全文の書き直しはしない。Issue 番号を渡された場合は、「Issue から設計する」の手順2〜5も当てはめる。
4. 変更後、ファイル間の整合を確認する。
   - `specification.md` の機能が `requirements.md` の機能要件に無い → 要件の追加漏れ
   - `specification.md` の動作・データ制約と `architecture.md` の実現方式が両立しない → 食い違いと必要な判断を PR本文に記録する
   - コードと文書が食い違う → **文書を正とし、コードの不具合として報告する**。文書をコードに合わせて直さない（利用者が確認するのは文書のため）。コードの修正は実装の作業で、このスキルでは行わない。報告では、食い違った箇所（文書の節、コードの場所）と文書の記述を一覧にして PR本文の「食い違い」と終わりの報告に示し、`/dev-process-kit:issue` で不具合として Issue にするよう利用者に勧める（会話や PR だけでは、マージ後に不具合として追跡されないため）。Issue はこのスキルでは起票しない。ただし、次の場合はコードの不具合として扱わない
     - Issue・設計PRの差分から設計が先行していると確認できる箇所
     - 新規作成モードで既存コードから起こした未マージの設計PRにおいて、まだ仕様として追認されていない記述とコードが食い違っている箇所（読み取り誤りか仕様の確認事項として PR本文の「食い違い」と PRコメントに示し、読み取り誤りと分かれば文書を直す）
     - なお、既存コードから起こした設計PRのマージ後に時間が経ってから差異が見つかった場合も、上記のとおり差異を一覧にして `/dev-process-kit:issue` で Issue にするよう勧め、コードを文書に合わせるか文書をコードに合わせるかの判断を利用者に委ねる
   - 人が仕様の変更として文書の更新を依頼した場合（「この実装を設計書に反映して」など）は、依頼に従って文書を直す
5. 更新した節と、変更しなかったファイルの理由を PR本文に記載し、「PRで確認する」に進む。

### ルーティング表

| 変わったもの | 更新するファイル |
| :--- | :--- |
| 目的、利用者、利用シナリオ、業務要件（人とシステムで回す業務の流れ）、機能要件、受け入れ基準、非機能目標、スコープ、用語 | `requirements.md` |
| 入力と結果、計算・検証規則、画面と操作可否、実際の状態遷移、データの意味・関連・制約、入出力形式、互換性、エラー・通知 | `specification.md` |
| 全体構成と境界、不変条件、責務と依存、技術選定、設計理由、永続化・整合性・移行、共通実装規約、非機能の実現方式、検証方針・重点リスク・検証限界 | `architecture.md` |
| 現在のクラス・関数の一覧、内部の呼び出し順序、詳細なデータアクセス手順 | 保守対象の設計文書には書かず、必要時に現在のコードから説明する |

迷ったら、**達成目標・期待動作・実現方式のどれか**で決めます。更新頻度や図の種類では決めません。混在する段落は分け、規則の全文を重複管理せず主たる記載先を参照します。境界例と情報を落とさないための扱いは [情報の性質による切り分け](references/policy.md#4-情報の性質による切り分け) を参照してください。

### ADR の書式と更新

`architecture.md` のADRは、[テンプレート](assets/templates/architecture.md)の番号付きタイトル（Title、レベル3）と本文5項目（レベル4）で記録します。本文はステータス（Status）、意思決定内容（Decision）、背景（Context）、影響（Consequences）、他に検討したもの（Alternatives Considered）の順です。更新モードで ADR や節を足すときも、テンプレートの HTML コメントは文書に写しません。番号・Status・不明事項の扱いは [ADR の記録と改定](references/policy.md#adr-の記録と改定) に従います。

決定の履歴は追記で残します。決定が変わったら新しい番号のADRを足し、新旧を相互に参照します。既存ADRの書式統一を求められた場合だけ、番号と決定内容を保持して該当箇所を整形できます。書式統一の中で決定内容は変えず、変えるべき決定は PRコメントで提案します。

## 書かないこと

- **テストケース・テスト手順** — テストコードを正とします。期待動作は仕様、検証方針・重点リスク・検証限界はアーキテクチャに残し、テストへの反映を未確認のまま削除しません
- **`tasks.md` / 実装タスク一覧** — このスキルの範囲外です。着手中の作業は GitHub Issue で管理します
- **事実・過去の経緯の創作** — 未決の設計は案を選んで書けますが、確認できない事実や過去の経緯は書きません
- **未決の印** — `仮定`・`未承認`・`仮案`・`TBD` などの印や、確認待ちを示す注記。どの言語の印も同じです（`Assumption`・`Unapproved`・`Tentative` など）。確認は PRコメントで行い、文書には決まった内容だけを書きます
- **現在の実装構造の写し** — 関数シグネチャや内部処理の転記は保守しません。必要時に AI が現在のコードを読み、Markdown や HTML などで図示・説明します。守るべき責務・制約と、その理由は設計文書に残します
- **維持できない粒度の記述** — 更新されない設計ドキュメントは「間違った地図」になります

## しないこと

- **実装** — テストやプロダクトコードは書きません

## PRで確認する

設計文書の作成・更新の依頼には、作業ブランチの作成、対象変更のコミット、push、PR作成・本文更新、未決事項への質問コメントの投稿までを含みます。操作ごとの許可や、設計内容の事前承認を会話で求めず、レビューできる PRにして URLを提示します。マージはユーザーの判断とします。

- 既存の設計用の作業ブランチや PRがあれば再利用し、今回の対象変更だけをコミットする。
- 設計の追加・変更は、実装の途中で必要になった場合（`dev-process-kit:implement` が止まり、利用者がこのスキルを呼んだ場合）も、統合ブランチ（設計PRのマージ先）から切った設計用のブランチで、設計文書だけの設計PRにする。実装ブランチ・実装PRには含めない。設計PRのマージで仕様が合意・凍結され、実装はそのマージを待って再開するため。
- PRの起票方法と本文は、対象リポジトリの規約・指定された PRテンプレートに従う。テンプレートの指定が無ければ、作成・本文更新のたびに次の順で探して読み直し、構成を記憶から補わない。
  - 対象リポジトリの `.github/`・リポジトリ直下・`docs/` にある `pull_request_template.md`、または `.github/PULL_REQUEST_TEMPLATE/` の中のファイル。
  - 対象リポジトリに無ければ、GitHub がテンプレートを引き継ぐ所有者の `.github` リポジトリの同じ場所（`gh api repos/<owner>/.github/contents/.github/pull_request_template.md --jq '.content' | base64 -d`）。
  - `gh pr create` は非対話ではテンプレートを本文に当てないため、テンプレートの見出しとコメントの指示に従って本文を組み立て、`--body-file` で渡す。テンプレートのコメントは本文に残さない。
- テンプレートや規約に関わらず、設計PRの本文には次の項目を必ず含める。設計PRのレビューと、後で `dev-process-kit:implement` が作業範囲を読むのに使うため。テンプレートに対応する節があればそこに書き、無ければテンプレートの節の後に見出しを足す。テンプレートが無ければ、この項目をそのまま見出しにする。
  - **概要と関連Issue** — 何をなぜ設計したか、関連Issue。関連Issueの書き方と、`Closes` ではなく `Refs` とする理由は、この節の最後の項目を参照。
  - **変更した節** — 更新したファイルと節、変更しなかったファイルとその理由
  - **食い違い** — 文書間・文書とコードの食い違いと、必要な判断。無ければ省く
  - **確認したこと** — 確認したこと（ファイル間の整合、Issue との突き合わせなど）と、確認していないこと（確認できなかった事実、不足情報）を分けて書く。確認していないことを確認済みとして書かない。
  - 各手順で PR本文に書くよう求めたもの（配置先の判断理由、既存コードから読み取った記述の一覧、`AGENTS.md` への参照追加の提案、作り直す節の分類など）も、該当するときは含める。
- 未決だった箇所で選んだ案と変更案は、本文の必須項目にせず、文書を完成品として書いた後に PRコメントで質問する（下の「選んだ案への質問」）。既存コードから読み取った現状の動作を仕様として追認するかの確認も、選んだ案とは区別して PRコメントで質問する。判断待ちがあっても PR作成前に止まらず、回答が必要なら Draft にする。回答を反映して対象の設計を整え、整合を確認するまで Draft を維持する。
- 選んだ案への質問は、PR作成・更新後に `gh pr comment <PR番号> --body-file <一時ファイル>` で別途投稿する。対象の節、文書に書いた案、理由、入力と期待結果の例、主要な代替案と影響を示し、「この案でよいか、別案ならどれか」を答えられる問いにする。既存の質問と回答を確認し、同じ質問を繰り返さず、新たな判断を求めるときだけ新規コメントを投稿する。
- 回答で案が変わったら、文書の該当箇所を決まった内容に書き換える。回答の経緯を示す注記は足さない。既存の文書に `仮定`・`未承認`・`TBD` などの未決の印（言語は問わない）が残っていれば、その箇所も最も妥当な案で書き換えて印を外し、同じように PRコメントで質問する。
- 設計だけで Issue は完了しないため、関連Issueは `Closes #<番号>` ではなく `Refs #<番号>` とする。Issue 1つごとに `Refs #<番号>` だけの行を書き、文の中に埋め込まない。`dev-process-kit:implement` はこの行を目印に同じ Issue の設計PRを探し、番号に触れただけの PR と区別するため。Issueが指定されていなければ、その確認だけを理由に止まらず、番号なしで PRを作る。

## 既存ファイルの扱い

`requirements.md` / `specification.md` / `architecture.md` は既存内容を踏まえて差分更新します。大きく作り直す必要がある場合も、節ごとの分類（残す / 消す / 別ファイルへ移す）と理由を PR本文に示し、変更案を差分として提出します。承認を会話で待たず、PR上で確認を受けます。確認できない事実を書き足しません。対象外の既存資料は、今回の依頼に移行・削除が含まれない限り変更しません。
