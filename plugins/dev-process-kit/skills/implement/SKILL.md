# implement Skill

## 概要・責務と原則

統合ブランチ（設計PRのマージ先となる `main` や `develop` など）にマージ・凍結された設計文書を正本として、Issue 1つにつき1つの実装PRで実装します（使い方: `/dev-process-kit:implement <issue番号>`）。

- **責務の境界**: プロダクトコード・テストの実装と実装PRの作成・更新だけを行う。設計文書の編集・設計PRの作成・Issue の起票や編集はせず、他スキルを代わりに実行しない。必要なときは止まって利用者に `/dev-process-kit:design <番号>`（設計の不足・修正）や `/dev-process-kit:issue`（範囲外の不具合・追加の仕様変更）の実行を頼む。外部仕様の変更は利用者が認識したうえで別 PR で合意するため。
- **仕様の凍結と内部設計の分離**: 設計PRのマージは仕様の合意と凍結を意味する。設計文書にある外部仕様の不足・未決・欠陥は仮案で実装せず止まる。設計文書に書かれていない内部設計は、細部のたびに止まると手戻りが増えるため止めずに決めてユニットテストで表す。正しい動作がすでに設計文書に書かれているバグ修正は、設計PRを経ずにこのスキルから始められる。
- **安全なコメント更新**: 同じ話題の記録コメントは古い内容で読者が迷わないよう書き換えるが、対象はエージェント自身が書いたと確信できる記録コメントに限る（手順: [PR の探索・作成・レビュー対応](references/pr-and-review.md#5-既存コメントの安全な書き換え)）。人のコメント・レビュー返信・判断を問う質問は新規コメントにする。

## 最初に確かめる

PR の特定方法と統合ブランチ取り込みの詳細は [PR の探索・作成・レビュー対応](references/pr-and-review.md) に従います。

1. `gh issue view <番号> --comments` で Issue を読む。
2. 設計文書は統合ブランチ上のリポジトリ直下の `docs/` にある4ファイル（`requirements.md`・`specification.md`・`architecture.md`・`tests.md`）とする。場所は `docs/` 固定で、リポジトリの規約や他の場所（リポジトリ直下など）にある同名ファイルでは変えない。`docs/` に4ファイルが1つも無ければ「設計文書が無い」とする（手順6）。ルートセットの `architecture.md`「全体構成と境界」のサービス索引や分割ディレクトリ（`specification/` 等）の索引リンクから辿れる子ファイルも設計文書に含める（索引から辿れないものは含めない）。英語など他言語の設計文書では対応する役割の節を読む。「差分が設計文書だけのPR」は変更ファイルが設計文書（新しく作る `docs/` の4ファイルを含む）だけのPRを指す。
3. 同じ Issue の未マージの実装PRを `Closes #<番号>` の独立行で探す（差分が設計文書だけの設計PRは除外）。
   - Ready for review の実装PRがある → [Ready for review の後: 指摘に対応する](references/pr-and-review.md#3-ready-for-review-の後-指摘に対応する) に進む。
   - Draft の実装PRがある → そのブランチに切り替え、統合ブランチに設計変更がマージされていれば取り込み、手順5・6を確認して「実装する」の続きを進める（ブランチもPRも作り直さない）。作業範囲と残作業は Issue、PR本文、差分から読み、設計文書の該当箇所と照合する。
4. 依頼されたPRの差分が設計文書だけなら設計PRなので対応せず、`/dev-process-kit:design` を呼ぶよう利用者に伝えて終える（実装PRは作らない）。
5. 統合ブランチを最新にし、作業範囲を決める。
   - 対象サービスのセット・対象の子ファイルを読む。
   - マージ済みの設計PRを `Refs #<番号>` の独立行（かつ差分が設計文書だけ）で探す。設計PRがあればその本文・レビュー・差分から変更仕様を把握して設計文書と照合し、無ければ Issue の変更要求を設計文書と照合して作業範囲を決める（無関係な変更は含めず、設計文書内の Issue 番号や実装状況のマーカーには依存しない）。
   - バグ報告では、起きている不具合そのものではなく、Issue が期待する正しい動作を設計文書と照合する。正しい動作が設計文書にあれば、コードの不具合として作業範囲にする。
6. 次のどれかに当たれば、実装を始めずに「設計が足りないとき」に進む。
   - 設計文書が無い（手順2）。
   - Issue の内容（バグ報告なら期待する正しい動作）が設計文書に書かれていない。
   - 作業範囲に `TBD`・`仮定`・`未承認`・`Assumption`・`Tentative` など言語を問わず未決の印が残っている（業務ルールの表の期待結果も含む）。

### 設計が足りないとき

1. ユーザーが意図して設計文書を残さない意向を示している場合は、足りない点をチャットで質問し、回答で決まった内容で実装する（設計PRは作らない）。
2. そうでなければ、同じ Issue の未マージ設計PRを `Refs #<番号>` で探す。
   - 設計PRがある → 作業を止め、そのマージを待つことを伝えて終える。
   - 設計PRが無い → 何が足りないか（無い文書・不足内容・残っている未決の印）を示し、`/dev-process-kit:design <番号>` で設計PRを作るよう頼んで終える（ブランチ・設計文書・設計PRは作らない）。
3. 設計PRがマージされたら、もう一度このスキルで実装を始める。

## 書き残す先

次のセッションや後から読む人が会話を持たずに困るものだけを残します（実況やコード・コミットを読めば分かることは書かない）。Issue は読むだけで書かず、PR 本文は最新に保ちます。

| 残す先 | 残すもの |
| :--- | :--- |
| 設計文書 | 書かない。残したほうがよい情報（判断理由、見つけた制約など）は PR コメントに「設計文書に残す候補」として書く |
| テストコード・コード | 内部設計の判断（ユニットテストを仕様として読めるように書いて表す） |
| PR 本文 | 概要、作業範囲、受け入れ基準とテスト、動作確認、設計文書に無かった判断、判断待ち |
| PR コメント | 人の判断を問う具体的な質問、設計文書に残す候補、設計文書に残すべきでない情報（デバッグ中の CI 結果など） |

## 実装する

1. 統合ブランチからブランチを作る（ブランチ名・作り方・worktree の有無は規約や `AGENTS.md`・指示に従う）。
2. 実装前のテスト成否を記録する（既存の失敗と新たに壊した失敗を区別するため）。
3. 設計文書の受け入れ基準と業務ルールを満たすように実装し、作業範囲の設計文書ごとに下の対応でテストを書く。フレームワークや細かい規約はプロジェクトに合わせるが、参考資料のテスト定義と「ユニットテストを先に書く進め方」は変えない。

   | 作業範囲の設計文書 | 書くテスト | 書く時期 | 参考資料 |
   | :--- | :--- | :--- | :--- |
   | `requirements.md` の業務要件 | シナリオテスト（機能をまたぐ業務の流れ） | 基本は実装の後 | [シナリオテスト](references/scenario-test.md) |
   | `specification.md` | インテグレーションテスト（1機能の振る舞いをブラックボックスで検証。純粋な計算規則は表の行に対応づけたユニットテストでもよい） | 基本は実装の後 | [インテグレーションテスト](references/integration-test.md) |
   | 詳細設計（文書にしない） | ユニットテスト（詳細設計の代わりとして仕様のように読む） | プロダクトコードより先（TDD） | [ユニットテスト](references/unit-test.md) |

   部品はユニットテスト（TDD）で作り、部品がそろって機能ができたらインテグレーションテストで、業務の流れが通るようになったらシナリオテストで確かめる。

   - `architecture.md` の制約はビルドの仕組みで強制できるものは強制し、できないものは PR レビューで照合する。非機能要件は `requirements.md` の目標を合否条件とする。プロジェクト固有のテストスコープ・ツール・テスト環境・品質ゲートと終了条件は `tests.md` に従う。
   - 人を含む受け入れテストは、実行と証拠集め（操作ログ、スクリーンショット、録画）を手伝えるが GO / NO-GO は人が判断するため、結果を確認済みとせず PR 本文で人の判断を待つ項目として示す。
   - 対のテストを実行する仕組みが無い場合も黙って省かず、確かめられなかった範囲を PR 本文の未確認に書く（限界を `tests.md` に残す必要があれば PR コメントに候補として書く）。
   - 業務ルールの表の行はテストデータにそのまま写し、設計文書の該当箇所と人が見比べられる名前・説明を付ける。
4. **合意済みの仕様だけを実装する。** 途中で見つかった設計の問題は下の「外部仕様と内部設計」で分けて扱う。
5. 設計文書とコードを突き合わせる。
   - 作業範囲内の食い違い → 文書を正としてコードを直す（文書の誤りなら手順4へ）。
   - 作業範囲外の食い違い → 直さない。食い違った箇所（文書の節、コードの場所）と文書の記述を一覧にして PR コメントと終わりの報告に示し、`/dev-process-kit:issue` での不具合起票を勧める（Issue は起票しない。設計PRマージ済みで別 Issue の実装待ちと確認できる箇所は不具合扱いしない）。
6. 途中で分かった考え・暗黙知・調査結果は設計文書には書かず PR コメントに残す（設計文書に残すべきものは「設計文書に残す候補」と明記）。設計文書は Issue・PR・コードから独立させ、未実装メモを残さない。
7. 品質ゲートを通し、終了条件を満たすまで進める（`tests.md`・規約・指示に従う。定めが無い場合の扱い・ガードレール・結果の分類は [品質ゲート](references/quality-gate.md)）。
8. コミット・push し、実装PRを作成・更新する（詳細・必須項目・`Closes #<番号>` は [PR の探索・作成・レビュー対応](references/pr-and-review.md#2-実装pr-の作成更新とコミット)）。
9. 品質ゲート・PR 本文・自動チェック指摘への対応まで終えて push してから `gh pr ready <PR番号>` で Ready for review にする（マージはユーザーの判断）。

### 外部仕様と内部設計

| 分類 | 当てはまるもの | 扱い |
| :--- | :--- | :--- |
| 外部仕様の問題（不足・未決・欠陥） | 設計文書に書かれた内容が足りない・未決である。または書かれたとおりに作ると受け入れ基準を満たせない、文書どうしが矛盾する、データ消失やセキュリティ問題が起きる | 止まって利用者に知らせ、別の設計PRのマージを待つ（「設計を直す必要があるとき」） |
| 外部仕様の追加変更（実装中の要望） | 凍結した仕様に問題はないが、実装中に利用者から外部仕様の変更を求められた | 止めずに作業中の Issue は凍結した仕様のまま完了させ、変更は新しい Issue として `/dev-process-kit:issue` で起票するよう伝える（迷っている場合は確認する） |
| 内部設計 | 設計文書に書かれていない細部で、どう決めても設計文書に反しないもの（部品分割、内部データ構造、処理順、未指定の文言や並び順など） | 止めずに最も妥当な案で決めてユニットテストで表し、PR 本文の「設計文書に無かった判断」に挙げる |

迷ったら、決めた内容が設計文書のどこかの記述と食い違うかで分けます（食い違うなら外部仕様、食い違わないなら内部設計）。

### 設計を直す必要があるとき

1. それまでの実装をコミットして実装ブランチに push する。実装PRがあれば Draft にし、設計変更待ちであることを PR 本文に書く。
2. 設計文書のどこがなぜ足りない・間違っているか（文書・節、実装で困ること、考えられる直し方）を示し、`/dev-process-kit:design <番号>` で別設計PRを作るよう頼んで終える（設計ブランチ・設計文書・設計PRは作らない）。
3. 設計PRが統合ブランチにマージされたら、統合ブランチを実装ブランチに取り込んで再開する。

### 判断待ちがある場合

設計以外の判断待ち（資格情報や実測結果の不足、レビュー指摘への対応方針など）は次のように扱う。

- 判断待ちの内容・実装済み範囲・検証結果・未完了項目を PR 本文に書いて Draft PR にし（Ready なら戻す）、解決まで Draft を維持する。
- PR 本文とは別に `gh pr comment <PR番号> --body-file <一時ファイル>` で、対象の箇所・理由・選べる案と影響を示して質問する（既存コメントを確認し同じ質問は繰り返さない）。
- 不足情報は仮定で補わない。ただし外部サービスのテスト環境の資格情報が作業環境に無い場合は、作業を止めずにテストダブルで置き換えたテストを書いて進め、未確認の範囲と理由を PR 本文に書く。接続テストの要否が未定なら PR コメントで確認して Draft を維持し、決まっていれば判断待ちにせず進める（詳細: [インテグレーションテスト](references/integration-test.md#結合の範囲)）。

## 出力形式

終わりに PR の URL と UAT で参考にする受け入れ基準（設計文書の該当箇所）を示します。設計PRマージ待ちで止めた場合は設計PR URL・止めた理由・実装済み範囲を、判断待ちがあれば Draft PR と質問コメントの URL・未確認事項を、作業範囲外の食い違いがあれば一覧と PR コメント URL を示して `/dev-process-kit:issue` での起票を勧めます。
