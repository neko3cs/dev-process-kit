# implement Skill

## 概要

設計文書に書かれたことを、Issue 1つにつき1つの実装PRで実装します。何を作るかは設計文書から読み、Issue は作業範囲と `Closes #<番号>` の紐付けに使います。

- **正本は設計文書です。** 業務要件と受け入れ基準は `requirements.md`、入力から結果が決まる規則は `specification.md` の業務ルールにあります。テストはその写しで、どの設計文書をどのレベルのテストで確かめるかは「実装する」の手順3の対応に従います。
- **設計PRのマージ後に実装します。** 設計PRのマージは、仕様の合意と凍結を意味します。設計文書に書かれた外部仕様の不足・未決・誤りを、実装PRの中で仮案にして実装しません。外部仕様を直す必要があれば、作業を止めて利用者に知らせ、別の設計PRで直してマージされるのを待ちます（「設計が足りないとき」「設計を直す必要があるとき」）。
- **設計文書は書きません。** 設計文書を書くのは `dev-process-kit:design` で、利用者が名前で呼んだときだけ動きます。このスキルから呼び出したり、同じ手順を代わりに行ったりせず、設計が必要なときは止まって、利用者に `/dev-process-kit:design <番号>` の実行を頼みます。設計文書に書かれていない内部設計は、このスキルが決めてユニットテストで表します（「外部仕様と内部設計」）。
- 正しい動作がすでに設計文書に書かれているバグ修正などは、設計PRを経ずにこのスキルから始められます。

このスキルでいう「統合ブランチ」は、設計PRのマージ先（`main` や `develop` など、リポジトリで統合に使うブランチ）を指します。

## 使い方

```
/dev-process-kit:implement <issue番号>
```

## 最初に確かめる

1. `gh issue view <番号> --comments` で Issue を読む。
2. 設計文書の場所を特定する。`dev-process-kit:design` が設計文書を置くときと同じ順で統合ブランチを探し、`requirements.md`・`specification.md`・`architecture.md` のどれかが最初に見つかった場所を設計文書の場所とする。セッションごとに探し方を変えない。
   1. リポジトリの配置規約で決まる場所（`AGENTS.md`・README などに書かれた設計文書の置き場所）
   2. `docs/` 配下
   3. リポジトリ直下

   - どこにも無ければ「設計文書が無い」とする（手順6）。
   - 見つかった場所のセットをルートのセットとする。ルートのセットの `architecture.md` の「全体構成と境界」にサービスごとのセットの索引があれば、そこに載ったセットも設計文書に含める。文書が同じ名前のディレクトリに分割されていれば（`specification/` など）、索引の文書（`specification.md` なら機能一覧）のリンクから子ファイルをたどる。索引から辿れないファイルは設計文書として扱わない。
   - 設計文書は日本語以外で書かれていることがある（見出しも訳されている）。このスキルが挙げる節の名前（「機能要件と受け入れ基準」「業務ルール」「全体構成と境界」など）は、その文書で同じ役割を持つ節を指す。
   - 以降でいう「設計文書」は、ルートのセットと索引に載ったセットの3ファイルと、その子ファイルを指す。「差分が設計文書だけのPR」は、変更したファイルが設計文書だけのPRを指す。統合ブランチに設計文書がまだ無い場合は、上の順で決まる配置先（規約で決まる場所、既存の `docs/`、リポジトリ直下）に3ファイルを足すだけのPRを指す。
3. 同じ Issue の未マージの実装PRを、本文の `Closes #<番号>` の行で探す（「同じ Issue の PR を探す」）。差分が設計文書だけのPRは設計PRなので、実装PRとして扱わない。
   - Ready for review の実装PRがある → 「Ready for review の後: 指摘に対応する」に進む。
   - Draft の実装PRがある → そのブランチに切り替え、統合ブランチに設計の変更がマージされていれば実装ブランチにマージし、手順6の確認をしてから「実装する」の続きを進める（ブランチもPRも作り直さない）。作業範囲と残作業は Issue、PR本文、差分から読み、設計文書の該当箇所と照合する。
4. 依頼されたPRの差分が設計文書だけなら、それは設計PRなので対応しない。そのPRのレビュー対応は `/dev-process-kit:design` を呼んで頼むよう利用者に伝えて終える。実装PRは新しく作らない。
5. 統合ブランチを最新にし、作業範囲を決める。
   - サービスごとのセットがあれば、Issue の対象のサービスのセットと、ルートのセットのうちサービスをまたぐ節を読む。分割された文書は、索引から対象の子ファイルだけを読む。
   - Issue の本文・コメントから対象の機能と変更要求を読み、マージ済みの設計PRを、本文の `Refs #<番号>` の行で探す（「同じ Issue の PR を探す」）。見つかった PR のうち、差分が設計文書だけのものを設計PRとする。
   - 設計PRがあれば、その本文・レビュー・差分から変更された仕様を把握し、現在の設計文書の該当箇所と照合して作業範囲を決める。無関係な変更は含めない。
   - 設計PRが無ければ（バグ修正など）、Issue の変更要求を設計文書の該当箇所と照合して作業範囲を決める。設計文書内のIssue番号や実装状況のマーカーには依存しない。
   - バグ報告の Issue では、Issue が期待する正しい動作（期待する動作、受け入れ条件など）を設計文書と照合する。起きている不具合そのもの（「ログイン画面でクラッシュする」など）は設計文書に書かれないため、照合の対象にしない。正しい動作が設計文書に書かれていれば、設計文書と食い違うコードの不具合として、その箇所を作業範囲にする。
6. 次のどれかに当たれば、実装を始めずに「設計が足りないとき」に進む。
   - 設計文書が無い（手順2）。
   - Issue の内容が設計文書に書かれていない。バグ報告では、Issue が期待する正しい動作が設計文書に書かれていない場合を指す（手順5）。正しい動作が書かれていれば、設計PRを作らずに「実装する」に進む。
   - 作業範囲に `TBD`・`仮定`・`未承認`・`仮案` などの未決の印が残っている（業務ルールの表の期待結果も含む）。印の言語は問わず、決まっていない・承認されていないことを示す語や注記はすべて未決の印とする（`Assumption`・`Unapproved`・`Tentative`・`To be decided` など）。設計文書を書く `dev-process-kit:design` はこれらの印を書かないため、残っていれば合意前の内容として扱う。

### 同じ Issue の PR を探す

同じ Issue の設計PR・実装PRは、PR本文にある次の目印の行で特定する。PR本文やタイトルの全文検索だけで決めない。番号に触れただけの PR（「#12 と同様に」など）や、別 Issue の PR まで拾い、取り違えると別 Issue の PR を再利用・更新してしまうため。ブランチ名は利用者が決めるため、目印に使わない。

| PR | 目印の行 | 書く場所 |
| :--- | :--- | :--- |
| 設計PR | `Refs #<番号>` | `dev-process-kit:design` の「PRで確認する」 |
| 実装PR | `Closes #<番号>` | 「コミット」節 |

目印の行は、`Refs #<番号>` または `Closes #<番号>` だけからなる1行とする。全文検索で候補を取り、目印の行を持つ PR だけに絞る。`<状態>` は、探す PR に合わせて `open` か `merged` にする。

```sh
gh pr list --state <状態> --search "#<番号> in:body" --limit 100 \
  --json number,title,body,isDraft,headRefName \
  --jq '.[] | select(.body | test("(?m)^(Refs|Closes) #<番号>\\s*$")) | {number, title, isDraft, headRefName}'
```

- 絞り込んだ PR のうち、差分が設計文書だけのものを設計PR、それ以外を実装PRとする（`gh pr diff <PR番号> --name-only`）。目印の行の種類は設計PRと実装PRの見分けに使わない。設計PRの本文に誤って `Closes` が書かれていても、差分で見分けられるようにするため。
- 目印の行を持つ PR が無いのに、全文検索の候補に対象 Issue の PR らしいもの（この決まりより前に作られた PR など）がある場合は、本文と差分を読んで対象 Issue の PR か確かめてから扱う。

### 設計が足りないとき

1. ユーザーが、意図して設計文書を残さない意向を示している場合は、足りない点をチャットで質問し、回答で決まった内容で実装する。設計PRは作らない。
2. そうでなければ、同じ Issue の未マージの設計PRを、本文の `Refs #<番号>` の行で探す（「同じ Issue の PR を探す」）。
   - 設計PRがある → 作業を止め、その設計PRのマージを待つことをユーザーに伝えて終える。
   - 設計PRが無い → 設計文書の何が足りないか（無い文書、Issue のどの内容が書かれていないか、残っている未決の印）を示し、`/dev-process-kit:design <番号>` を実行して設計PRを作るよう利用者に頼んで終える。ブランチ・設計文書・設計PRは作らない。
3. 設計PRがマージされたら、もう一度このスキルで実装を始める。

## 書き残す先

会話の中だけにあった考えは、次に読む人には届きません。次のセッションや後から読む人に必要な考え・暗黙知・調査結果は、生じたときに書き残します。

| 残す先 | 残すもの |
| :--- | :--- |
| 設計文書 | 書かない。外部仕様の変更が必要なら止まる（「設計を直す必要があるとき」）。設計文書に残したほうがよい情報（判断の理由、見つけた制約など）は、PR コメントに「設計文書に残す候補」として書き、利用者が後で `dev-process-kit:design` で反映できるようにする |
| テストコード・コード | 内部設計の判断。ユニットテストを仕様として読めるように書いて表す |
| PR本文 | PRの概要、確認状況の要約、動作確認 |
| PR コメント | 人の判断を問う具体的な質問、設計文書に残すべきでない情報（デバッグ中の CI の結果など） |

- Issue は読むだけで、書かない。
- 残すのは、次に読む人が会話を持たずに困るものに限る。作業の実況や、コードやコミットを読めば分かることは書かない。
- 同じ話題の PR コメント（方針の決定など）の内容が変わったら、新しいコメントを足さず、既存のコメントを書き換える（`gh api -X PATCH repos/{owner}/{repo}/issues/comments/<コメントID> -f body=...`）。PR本文も最新に保つ。古い決定が並ぶと、次に読む人が迷うため。ただし、コードへの指摘へのリプライと、人に判断を問うコメントは新しく書く（書き換えでは通知が飛ばないため）。
  - 書き換えるのは、エージェントが書いたコメントだけ。コメントの投稿者（`gh issue view <番号> --json comments` または `gh pr view <番号> --json comments` の `author.login`）が、`gh api user --jq .login` で調べた自分のアカウントと一致し、かつ内容からエージェントが書いたと分かるもの（このスキルの手順で書いた調査結果・経緯など）に限る。他人のコメントは、権限があっても書き換えない。人の書いた内容が変わってしまうため。
  - 同じアカウントでも、利用者が自分で書いたコメントは書き換えない。エージェントが書いたものか判断できなければ、書き換えない。
  - 書き換えられないコメントの内容が古くなったら、新しいコメントで補足する（どのコメントの、何が変わったかを示す）。

## 実装する

1. 統合ブランチからブランチを作る。ブランチ名と作り方は、リポジトリの規約や利用者の指示に従う。`AGENTS.md` に指示（worktree を使わない、など）があれば従う。
2. 実装前のテストの成否を記録する（後で「元々失敗していたテスト」と「新たに壊したテスト」を区別するため）。
3. 設計文書の受け入れ基準と業務ルールを満たすように実装し、それを確かめるテストを、作業範囲の設計文書ごとに次の対応で書く。各テストの定義（設計の方式、結合の範囲、書く時期、カバレッジ）と書き方は、対応する参考資料に従う。

   | 作業範囲の設計文書 | 書くテスト | 書く時期 | 参考資料 |
   | :--- | :--- | :--- | :--- |
   | `requirements.md` の業務要件 | シナリオテスト。機能をまたいで業務の流れを通し、システムが担う部分を確かめる | 基本は実装の後 | [シナリオテスト](references/scenario-test.md) |
   | `specification.md` | インテグレーションテスト。モジュールを結合し、1つの機能の振る舞いが仕様どおりかをブラックボックスで確かめる。画面・保存・外部連携を介さずに入力から結果が決まる計算規則は、表の行に対応づけたユニットテストでもよい | 基本は実装の後 | [インテグレーションテスト](references/integration-test.md) |
   | 詳細設計（文書にしない） | ユニットテスト。仕様として読めるように書き、詳細設計の代わりにする | プロダクトコードより先（TDD） | [ユニットテスト](references/unit-test.md) |

   部品はユニットテストのテスト駆動のサイクルで作り、部品がそろって機能ができたらインテグレーションテストで、業務の流れが通るようになったらシナリオテストで確かめる。

   - `architecture.md` の制約は、構造で強制できるものはビルドの仕組みで強制し、できないものは PR のレビューで照合する。非機能要件は `requirements.md` の目標を合否条件として確かめる。
   - 人を含む業務全体の受け入れテストは、実行と証拠集め（操作ログ、スクリーンショット、録画）を手伝えるが、GO / NO-GO は人が判断する。結果を確認済みとして扱わず、PR本文で人の判断を待つ項目として示す。
   - テストフレームワーク、ツール、テストの書き方の細かい規約は、プロジェクトの既存のテスト・規約と利用者の指示に合わせる。参考資料で定めたテストの定義と、ユニットテストを先に書く進め方は変えない。
   - 対のテストを実行できる仕組みがプロジェクトに無い場合（シナリオテストの環境が無いなど）も、黙ってユニットテストだけで済ませない。確かめられなかった範囲を PR本文の未確認に書く。仕組みが無いことと検証の限界を `architecture.md` の「検証方針と重点リスク」に残す必要があれば、手順6に従って PR コメントに候補として書く。
   - 業務ルールの表の行は、テストのデータとしてそのまま写す。テスト名か説明に、設計文書の該当箇所が分かる言葉を含め、人が表と見比べられるようにする。
4. **設計文書に書かれた合意済みの仕様だけを実装する。** 実装の途中で見つかった設計の問題は、「外部仕様と内部設計」で分けて扱う。外部仕様の不足・未決・誤りなら、実装PRの中で仮案にせず、「設計を直す必要があるとき」に従う。内部設計の判断なら、止まらずに決めてユニットテストで表し、PR本文の「設計文書に無かった判断」に挙げる。
5. 設計文書とコードを突き合わせる。
   - 作業範囲の中で食い違いがあれば、文書に記載した仕様を正としてコードを直す（利用者が確認するのは文書で、コードはあまり読まないため）。文書をコードに合わせて書き換えない。文書のほうが間違っていると判断したら、手順4に従う。
   - 作業範囲の外で見つけた食い違いは、直さずに PR コメントで知らせる（別の不具合として扱うため）。
6. 実装の途中で分かった考え・暗黙知・調査結果は、設計文書には書かない。仕様を変える必要があるものは、手順4に従う。設計文書に残したほうがよいもの（判断の理由、見つけた制約など）は、PR コメントに「設計文書に残す候補」として書く。それ以外で残すべきものも PR コメントに書く。
   - 設計文書は Issue・PR・コードから独立して仕様を理解できる状態に保ち、未実装でこれから実装が必要であることを示すメモは残さない。実装済み・保留の範囲は PR本文で管理する。
7. プロジェクトの品質ゲート（リポジトリの規約や利用者の指示で決まる検証）を通す。手順2で記録した元々の失敗は無視してよいが、新たに失敗するようになったテストは直す。
8. コミットして push し、実装PRを作る（または本文を更新する）。PRの作り方と本文の書式は、リポジトリの規約や利用者の指示に従う。PR本文と PR コメントの言語も規約や指示に従い、決まっていなければ設計文書と同じ言語で書く。下の必須項目の見出しも、本文の言語に訳す。Ready にする前なら Draft で作り、コミットのたびに push してよい。
   - PRテンプレートの指定が無ければ、作成・本文更新のたびに次の順で探して読み直し、構成を記憶から補わない。対象リポジトリの `.github/`・リポジトリ直下・`docs/` にある `pull_request_template.md`、または `.github/PULL_REQUEST_TEMPLATE/` の中のファイル。無ければ、GitHub がテンプレートを引き継ぐ所有者の `.github` リポジトリの同じ場所（`gh api repos/<owner>/.github/contents/.github/pull_request_template.md --jq '.content' | base64 -d`）。
   - `gh pr create` は非対話ではテンプレートを本文に当てないため、テンプレートの見出しとコメントの指示に従って本文を組み立て、`--body-file` で渡す。テンプレートのコメントは本文に残さない。
   - テンプレートや規約に関わらず、実装PRの本文には次の項目を必ず含める。Draft から再開するときや Ready の後に指摘へ対応するとき、作業範囲を PR本文から読むため（「最初に確かめる」、「Ready for review の後: 指摘に対応する」）。テンプレートに対応する節があればそこに書き、無ければテンプレートの節の後に見出しを足す。テンプレートが無ければ、この項目をそのまま見出しにする。
     - **概要と関連Issue** — 何をなぜ実装したか、`Closes #<番号>`（「コミット」節）
     - **作業範囲** — 設計文書のどの節を実装したか、実装済みの範囲と保留・未完了の範囲
     - **受け入れ基準とテスト** — 設計文書の受け入れ基準・業務要件・仕様ごとの対応するテストとその検証レベル（シナリオ・インテグレーション・ユニット）。対のテストを書けなかった範囲とその理由
     - **動作確認** — 「確認済み」と「未確認」に分けて書く（次の項目）
     - **設計文書に無かった判断** — 内部設計として決めた細部と、それを表すユニットテスト（「外部仕様と内部設計」）。無ければ省く
     - **判断待ち** — 判断待ちの内容、または設計PRのマージを待っていることとその設計PR（「判断待ちがある場合」「設計を直す必要があるとき」）。無ければ省く
   - 動作確認は「確認済み」と「未確認」に分ける。確認済みには、実際に実行・目視した内容（テストの実行、受け入れ基準との突き合わせなど）だけを、どの環境で確認したかを添えて書く。確認していないことは、理由とともに未確認に書く。確認していないことを確認済みとして書かない（レビュアーが確認済みの記述を信じて見落とすため）。
9. Ready にする前に、push するものをすべて片付ける。品質ゲート、PR本文、自動チェック（セキュリティレビューなど）の指摘への対応まで終えて push してから、`gh pr ready <PR番号>` で Ready for review にする。Ready の後の push は CI のやり直しになるため（次節）。マージはユーザーの判断で、このスキルの範囲はここまで。

### 外部仕様と内部設計

実装の途中で見つかった設計の問題は、止まるかどうかを次で分けます。設計文書は外部設計までを書き、内部設計を書かないため、細部のたびに止まると手戻りが増えるからです。

| 分類 | 当てはまるもの | 扱い |
| :--- | :--- | :--- |
| 外部仕様 | 設計文書に書かれた内容（受け入れ基準、業務要件、業務ルールの表、画面操作・状態・入出力・エラーなどの仕様、`architecture.md` の制約）を変える・足す必要がある。または、書かれたとおりに作ると受け入れ基準を満たせない、文書どうしが矛盾する、データ消失やセキュリティ上の問題が起きる | 仕様変更なので止まって利用者に知らせる（「設計を直す必要があるとき」） |
| 内部設計 | 設計文書に書かれていない細部で、どう決めても設計文書の記述に反しないもの（部品の分け方、内部のデータ構造、処理の順序、文書に指定の無い文言や並び順など） | 止まらない。最も妥当な案で決め、ユニットテストで表す。PR本文の「設計文書に無かった判断」に挙げ、レビューで見てもらう |

迷ったら、決めた内容が設計文書のどこかの記述と食い違うかで分けます。食い違うなら外部仕様、食い違わないなら内部設計です。

#### 実装中に利用者から仕様変更を求められたとき

利用者から実装中に外部仕様の変更を求められても、作業中の Issue は凍結した仕様のまま完了させます。変更は新しい Issue として起票し（`/dev-process-kit:issue`）、設計・実装をやり直すよう利用者に伝えます。進めている案件を途中で動かすと、何が合意済みかが分からなくなるためです。

ただし、変更の理由が上の表の外部仕様の問題（そのまま作るとデータが消える、など）に当たる場合は、「設計を直す必要があるとき」に従って止まります。今の仕様のまま完了させてよいか利用者が迷っている場合は、どちらにするかを利用者に確認します。

### 設計を直す必要があるとき

実装の途中で、外部仕様の不足・未決が見つかった、またはマージ済みの設計が間違っていると判断したら、AI が独断で仕様を書き換えたことにしないため、実装を止めて利用者に知らせ、設計を先に直します。内部設計の判断だけなら止まりません（「外部仕様と内部設計」）。

1. それまでの実装をコミットして実装ブランチに push する。実装PRがあれば Draft にし、設計の変更を待っていることを PR本文に書く。
2. 設計文書のどこがなぜ足りない・間違っているか（該当する文書と節、実装で困ること、考えられる直し方）を示し、`/dev-process-kit:design <番号>` を実行して設計PRを作るよう利用者に頼んで終える。設計用のブランチ・設計文書・設計PRは作らない。設計PRは統合ブランチから切ったブランチで作られ、実装ブランチの変更は含まない。
4. 設計PRが統合ブランチにマージされたら、統合ブランチを実装ブランチにマージし、直った設計に沿って実装を再開する。

### 判断待ちがある場合

設計（仕様と設計判断）についての判断待ちは、実装PRで扱わず「設計を直す必要があるとき」に従います。それ以外で人の判断を待つ場合（資格情報や実測結果の不足、レビュー指摘への対応方針など）は、次のようにします。

- 判断待ちの内容、実装した範囲、検証結果、未完了項目を PR本文に記載して Draft PRを作成・更新する。判断を反映し、必要な検証を終えるまで Draft を維持する。すでに Ready なら Draft に戻す。
- PR作成・更新後に、PR本文とは別に新規コメント（`gh pr comment <PR番号> --body-file <一時ファイル>`）で質問する。対象の箇所、判断が必要な理由、選べる案とそれぞれの影響を示し、答えやすい問いにする。既存のコメントと回答を先に読み、同じ質問を繰り返さない。
- 資格情報や実測結果などの不足は仮定で補わない。制約・進めた範囲・必要な情報を具体的に示す。PR URLと質問コメントを提示し、レビューできる状態で終了する。

## Ready for review の後: 指摘に対応する

Ready の PR への push は、**ひとまとまりの対応ごとに1回** にする。push するたびに実行中の CI が取り消されて最初からやり直しになり、途中の状態でレビュアーに通知も飛ぶため。CI の所要時間など、リポジトリに固有の事情は各リポジトリの `AGENTS.md` に従う。

1. Issue、PR の差分と PR本文（受け入れ基準ごとの対応するテスト）を設計文書と照合して作業範囲を読み、PR のレビューとコメントを読んで、そのとき来ている指摘をすべて把握する。自動チェック（セキュリティレビューなど）の指摘も、人のレビューの指摘と同じに扱う。
2. 指摘をすべて直す。直し方は「実装する」の手順3〜6に従う。指摘を直すために設計を変える必要があれば、「設計を直す必要があるとき」に従う。コミットは指摘ごとに分けてよいが、1件直すたびに push しない。
3. 残したほうがいい考え・暗黙知・調査結果（直し方を選んだ理由、見つけた制約など）が生じたら、設計文書には書かず、手順6で PR に新規コメントとして書く。設計文書に残したほうがよいものは「設計文書に残す候補」と分かるように書く。
4. ローカルで品質ゲートを通す。
5. 1回 push し、PR本文の動作確認を更新する。
6. コードに付いた指摘ごとに、その指摘へのリプライとして対応を書く（どう直したか、直さなかった・別の直し方を採った理由など）。`gh api repos/{owner}/{repo}/pulls/<PR番号>/comments/<コメントID>/replies -f body=...` でそのスレッドに返す。リプライへのリプライは API が受け付けないため、`<コメントID>` にはスレッドの最初のコメントの ID を使う。コードに付いていないコメントへの定型返信は不要だが、質問への回答は読み取り、実装・テストとPR本文に反映する。新たな判断が必要なら別途新規コメントで質問する。手順3で PR コメントに回したものは、ここで新規コメントとして書く。push の後に書くのは、コメントが push 済みのコミットを指せるようにするため。

まれに次の状況になる。

- **直している途中で新しい指摘が届いた**: 新しい指摘も含めてすべて直し、品質ゲートを通してから1回 push する。
- **指摘の一部が人の判断待ち**: 直した分を先に1回 push し、「判断待ちがある場合」に従って Draft に戻し、確認事項を PR本文と該当のレビュースレッドに残す。判断が出て直したら、もう一度 push する。

## コミット

作業ブランチ上では、コミット・push・PR作成・PR本文更新・PR へのコメント・Ready for review への変更まで、操作ごとの許可をユーザーに求めずに進める。マージはユーザーの判断とする。

コミットメッセージに Issue 番号を含める（`Refs #<番号>`）。

実装PRの本文には、作成時から `Closes #<番号>` だけの行を書く。文の中に埋め込まない。この行が、同じ Issue の実装PRを探すときの目印になる（「同じ Issue の PR を探す」）。判断待ちで Draft のあいだも `Refs` にしない。実装PRは Issue 1つにつき1つで、判断待ちが残るあいだは Draft のままマージされないため、マージされる時点では Issue は完了している。`Refs` で作ると Ready にするときに書き換え忘れ、マージ後も Issue が残る。

## 出力形式

終わりに、PRのURLと、UATで参考にする受け入れ基準（設計文書の該当箇所）を示す。設計PRのマージを待って止めた場合は、設計PRのURL、止めた理由、実装済みの範囲を示す。判断待ちがあれば、Draft PRと質問コメントのURL、未確認事項を示す。
