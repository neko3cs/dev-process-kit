# 参考資料: テスト駆動での実装手順

`SKILL.md` の「実装する」の手順3で、テストとプロダクトコードを書くときに読む。判断の根拠は [講演の要約](tdd-bootcamp-2020-wada.md) にある。

テストは、どのレベルでも、対応するプロダクトコードより先に書く（テスト駆動開発、TDD）。TDD は品質保証の手段ではなく、コードを綺麗に保ちながら安心して開発を進めるための設計手法として扱う。歩幅を小さく保ち、手戻りを防ぐ。詳細設計を文書にしないこのプロセスでは、先に書くユニットテストが詳細設計の代わりになる。

## 二重のループで進める

設計文書から起こすテストを外側、その実現に必要な部品のテストを内側として、同じ Red → Green → Refactor のサイクルを入れ子にして回す。

| ループ | テスト | TODO リストの元 |
| :--- | :--- | :--- |
| 外側 | シナリオテスト、インテグレーションテスト | 作業範囲の `requirements.md` の業務要件と受け入れ基準、`specification.md` の業務ルール・画面操作・状態・入出力 |
| 内側 | ユニットテスト | 外側のテストを通すために必要な振る舞い |

1. 外側の TODO リストから1項目を選び、シナリオテストかインテグレーションテストを書いて、意図した理由で失敗することを確かめる（外側の Red）。
2. 外側のテストを通すために必要な部品を、内側の TODO リストに分解し、ユニットテストで1項目ずつサイクルを回す。
3. 外側のテストが通ったら（外側の Green）、テストを保ったまま全体を整える（外側の Refactor）。外側の TODO リストの次の項目に進む。

入力から結果が決まる計算規則を表の行に対応づけたユニットテストで確かめる場合（`SKILL.md` の手順3の対応）は、その表の行が外側の TODO リストの項目になり、ユニットテストが外側のテストを兼ねる。

## TODO リストを作る

実装を始める前に、「これが通れば仕様を満たす」と言える単位まで小さなテストケースに分解し、リストにする。

- 外側のリストは、設計文書の受け入れ基準・業務要件の流れ・業務ルールの表の行をそのまま項目にする。設計文書に無い項目を足さない。設計文書に無いケースに気づいたら、仮の期待結果で項目にせず、`SKILL.md` の手順4に従う。
- 内側のリストは、外側のテストを通すのに必要な振る舞いを小さく分解する。例（FizzBuzz）: 「1を渡すと"1"を返す」「3の倍数で"Fizz"を返す」「5の倍数で"Buzz"を返す」「15の倍数で"FizzBuzz"を返す」。
- 最も簡単で、次のテストへの足がかりになるものから着手する。
- 作業中に新しいケースに気づいたら、その場でリストに足す（外側のリストに足す場合は上の制約に従う）。

## 1項目ずつ Red → Green → Refactor を回す

リストから1項目だけを選び、次を順に行う。複数の項目を同時に進めない。

### Red（失敗するテストを書く）

- まだ存在しないクラス・メソッド・画面に対して、理想の使われ方（インターフェース）を思い描きながらテストを先に書く。
- テストを実行し、意図した理由で失敗することを確かめる。コンパイルエラー（ビルド失敗）も正当な Red。
- 想定と違う理由で失敗した、または誤って通ってしまった場合は、何も検出できないテストになっていないかを確かめてから次に進む。
- 外側のテストを実行する仕組みがプロジェクトに無い場合は、黙ってユニットテストだけで済ませず、`SKILL.md` の手順3の扱いに従う。Red を確かめられなかったことも、PR本文の未確認に書く。

### Green（最短でテストを通す）

テストを通す実装は、状況に応じて次の3つから選ぶ。どれを選んでも、Green になるまでは他のことを考えず、最短で通すことを優先する。

1. **仮実装（Fake It）**: 期待値をハードコードして、すぐに Green にする（例: `return "1";`）。正しさや美しさは後回しにする。
2. **明白な実装（Obvious Implementation）**: 実装が自明で確信がある場合は、最初から正しいコードを書く。
3. **三角測量（Triangulation）**: 一般化の方向に確信が持てない場合は、もう1つテストケース（リストの次の項目）を足し、2つの具体例から一般化を導く。

確信が持てなければ、明白な実装ではなく仮実装か三角測量を選ぶ。

### Refactor（テストを保ったまま綺麗にする）

- Green を保ったまま、重複の除去・一般化・命名の改善をする。
- 小さな変更ごとにテストを実行し、Green のままであることを確かめる。崩れたら直前の変更を見直す。
- プロダクトコードだけでなく、直前に書いたテストコードも整える。

サイクルを終えたら、リストの項目に印を付けて次の項目に進む。リストが空になるまで繰り返す。

## テストを仕様として読めるように書く

テストコードは、実装を読まなくても仕様が分かる「動く仕様書」として書く。Red を書く最初の時点から、次の構造で書く（肥大化してから直すのではない）。

- **テストの言葉**: 設計文書と同じ言葉で書く。日本語の設計文書なら日本語で書く。リポジトリにテスト名の言語の規約があれば、それに従う。
- **仕様の文脈でまとめる**: 関連するテストケースを、言語・フレームワークのグループ化の仕組みでまとめ、グループ名を仕様を表す自然文にする。外側のテストは、設計文書の節や規則の名前をグループ名に使い、人が設計文書と見比べられるようにする。
  - Java（JUnit 5）: `@Nested class 数を文字列に変換する { ... }`
  - TypeScript（Jest / Vitest）: `describe("数を文字列に変換する", () => { ... })`
  - C#（xUnit）: 入れ子クラス `public class 数を文字列に変換する { ... }`
  - Swift（XCTest）: メソッド名で文脈を表すか、`XCTestCase` を仕様ごとに分ける
- **テストケース名**: 入力に対してどう振る舞うべきかを、期待結果まで含めた自然文にする（例: `_3を渡すと文字列Fizzを返す`）。業務ルールの表の行を写したテストは、どの行かが分かる名前にする。
  - テスト名を識別子（メソッド名）として書く言語（Java、C#、Swift など）では、数字から始まる名前は使えないため、先頭に `_` を付ける。
  - テスト名を文字列として書くフレームワーク（Jest / Vitest の `it` など）では、`_` を付けずに自然文をそのまま使う。
- テストが増えて読みにくくなったら、この構造に沿ってグループ分けと名前を直す。テストコードはプロダクトコードと同じか、それ以上に丁寧に保守する。

例（Java / JUnit 5、FizzBuzz）:

```java
class FizzBuzzTest {
    private FizzBuzz fizzbuzz;

    @BeforeEach
    void 前準備() {
        fizzbuzz = new FizzBuzz();
    }

    @Nested
    class 数を文字列に変換する {
        @Test
        void _1を渡すと文字列1を返す() {
            assertEquals("1", fizzbuzz.convert(1));
        }
    }

    @Nested
    class _3の倍数のときは数の代わりにFizzに変換する {
        @Test
        void _3を渡すと文字列Fizzを返す() {
            assertEquals("Fizz", fizzbuzz.convert(3));
        }
    }
}
```

## 場面ごとの扱い

- **バグ修正**: まず不具合を再現する失敗するテストを書く（Red）。テストのレベルは、不具合が破っている設計文書に対応するレベルにする（`SKILL.md` の手順3の対応）。
- **レビュー指摘への対応**: 振る舞いを変える指摘は、先にその振る舞いのテストを足すか直してから、プロダクトコードを直す。
- **テストで確かめる振る舞いが無い変更**: 設定ファイルや文書だけの変更、生成されたコードなどには、このサイクルを求めない。
