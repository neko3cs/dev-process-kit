# 参考資料: PR の探索・作成・レビュー対応とブランチ取り込み

`SKILL.md` で同じ Issue の PR を探すとき、実装PRを作成・更新するとき、Ready for review 後の指摘に対応するとき、統合ブランチを取り込むとき、コメントを書き換えるときに読む。

## 1. 同じ Issue の PR を探す

同じ Issue の設計PR・実装PRは、PR 本文にある目印の独立行で特定する。全文検索だけで決めると番号に触れただけの別 Issue の PR を誤って再利用・更新してしまうため。ブランチ名も目印に使わない。

| PR | 目印の行（この1行のみ、文中に埋め込まない） |
| :--- | :--- |
| 設計PR | `Refs #<番号>` |
| 実装PR | `Closes #<番号>` |

`<状態>` は探す PR に合わせて `open` か `merged` にする。補助スクリプトを使うと、`Refs`/`Closes` の独立行での絞り込みと `gh pr diff --name-only` による設計PR/実装PRの分類をまとめて行える。

```bash
python3 scripts/find-issue-prs.py <番号> --state <open|merged> [--design-doc <パス> ...]
```

- 差分が設計文書だけのものを `design_prs`、それ以外を `impl_prs` とする（目印の行の種類ではなく差分で判定するため、誤って `Closes` が書かれた設計PRも見分けられる）。
- 目印の行を持つ PR が無い場合は `fallback_candidates` に全文検索の候補が出るため、ルール導入前の PR らしいものがあれば本文と差分を読んで確かめてから扱う。

## 2. 実装PR の作成・更新とコミット

作業ブランチ上では、コミット・push・PR 作成・PR 本文更新・コメント・Ready for review への変更まで、操作ごとの許可を求めずに進める（マージはユーザーの判断）。

- コミットメッセージに `Refs #<番号>` を含める。
- 実装PR の本文には、作成時から `Closes #<番号>` だけの独立行を書く（Draft のあいだも `Refs` にしない。書き換え忘れでマージ後に Issue が残るのを防ぐため）。
- PR 本文・コメントの言語は規約や指示に従い、無ければ設計文書と同じ言語で書く（下の必須見出しも訳す）。
- **PR テンプレートの探索**: 指定が無ければ、作成・本文更新のたびに `python3 scripts/find-pr-template.py [-R <owner>/<repo>]` で探して読み直す（対象リポジトリの `.github/`・直下・`docs/`・`.github/PULL_REQUEST_TEMPLATE/` → 無ければ所有者の `.github` リポジトリ）。非対話では自動適用されないためテンプレートの見出しと指示に従って本文を組み立て `--body-file` で渡し、テンプレートのコメントは残さない。

### 実装PR 本文の必須項目

テンプレートや規約に関わらず、次の項目を必ず含める（Draft 再開や Ready 後の指摘対応で作業範囲を読むため）。テンプレートに対応する節があればそこに書き、無ければ末尾に足す。

- **概要と関連Issue** — 何をなぜ実装したか、`Closes #<番号>` の独立行
- **作業範囲** — 設計文書のどの節を実装したか、実装済みと保留・未完了の範囲
- **受け入れ基準とテスト** — 設計文書の受け入れ基準・業務要件・仕様ごとの対応テストと検証レベル（シナリオ・インテグレーション・ユニット）。対のテストを書けなかった範囲と理由
- **動作確認** — 「確認済み」と「未確認」に分ける。確認済みには実際に実行・目視した内容だけを環境つきで書き、実行しなかった検証やテストダブル代替範囲は理由つきで未確認に書く（未確認を確認済みと書かない）
- **設計文書に無かった判断** — 内部設計として決めた細部とそれを表すユニットテスト（無ければ省く）
- **判断待ち** — 判断待ちの内容、または設計PRのマージを待っていることとその設計PR（無ければ省く）

## 3. Ready for review の後: 指摘に対応する

Ready の PR への push は**ひとまとまりの対応ごとに1回**にする（push ごとに CI がやり直しになり、途中の状態で通知も飛ぶため）。CI の所要時間など固有事情はリポジトリの `AGENTS.md` に従う。

1. Issue、PR 差分、PR 本文を設計文書と照合して作業範囲を読み、レビューとコメントから来ている指摘をすべて把握する（自動チェックの指摘も人のレビューと同じに扱う）。
2. 指摘をすべて直す（直し方は `SKILL.md` の「実装する」手順3〜6。設計変更が必要なら「設計を直す必要があるとき」に従う）。コミットは指摘ごとに分けてよいが、1件ごとに push しない。
3. 残すべき考え・暗黙知・調査結果が生じたら、設計文書には書かず手順6で PR に新規コメントとして書く（設計文書に残したほうがよいものは「設計文書に残す候補」と明記）。
4. ローカルで品質ゲートを通す。
5. 1回 push し、PR 本文の動作確認を更新する。
6. コードに付いた指摘ごとに、そのスレッドへリプライで対応を書く（どう直したか、直さなかった・別案を採った理由など）。
   ```sh
   gh api repos/{owner}/{repo}/pulls/<PR番号>/comments/<コメントID>/replies -f body=...
   ```
   リプライへのリプライは API が受け付けないため、`<コメントID>` にはスレッドの最初のコメント ID を使う。一般コメントへの定型返信は不要だが、質問への回答は実装・テスト・PR 本文に反映し、新たな判断が必要なら新規コメントで質問する。手順3の記録もここで新規コメントにする（push 後に書くことで push 済みコミットを指せるため）。

例外状況:
- **直している途中で新しい指摘が届いた**: 新しい指摘も含めて直し、品質ゲートを通してから1回 push する。
- **指摘の一部が人の判断待ち**: 直した分を先に1回 push し、「判断待ちがある場合」に従って Draft に戻し、確認事項を PR 本文と該当スレッドに残す。

## 4. 統合ブランチの取り込み

取り込み方法（マージか rebase か）はリポジトリの規約や利用者の指示に従い、指定が無ければマージで取り込む。

- **push 済みの実装ブランチを rebase で更新するとき**: `--force` ではなく `git push --force-with-lease` を使う。リモートの更新と競合して拒否された場合は `--force` で上書きせず、リモートの変更を確認してから利用者に相談する。
- **Ready for review の後**: レビュー中の差分やコメント追跡が壊れるため、rebase と force push は原則避ける。規約でマージコミットが禁止されているか利用者から rebase の指示がある場合だけ rebase して `--force-with-lease` で更新し、それ以外はマージにするか rebase してよいか利用者に確認する。

## 5. 既存コメントの安全な書き換え

同じ話題の記録コメント（方針の決定など）を更新するときは、次を満たすコメントだけを `PATCH` で書き換える。

```bash
gh api -X PATCH repos/{owner}/{repo}/issues/comments/<コメントID> -f body=...
```

- `gh pr view <番号> --json comments` の `author.login` が `gh api user --jq .login` と一致し、かつ内容からエージェントが書いたと分かるものに限る。
- 他人のコメント・利用者が自分で書いたコメント・判断できないコメントは書き換えない。書き換えられないコメントが古くなったら、どのコメントの何が変わったかを示す新規コメントで補足する。
