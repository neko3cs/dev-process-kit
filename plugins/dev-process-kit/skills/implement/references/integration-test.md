# 参考資料: インテグレーションテスト

`SKILL.md` の「実装する」の手順3で、インテグレーションテストを書くときに読む。

## 定義

| 項目 | 内容 |
| :--- | :--- |
| 呼び方 | 結合テスト（JSTQB の統合テスト、integration testing） |
| 確かめる設計 | `specification.md` |
| 対象 | モジュール・パッケージ・クラスを結合したときに、1つの機能が仕様どおりに動くか。画面を操作することもある。機能をまたいだ業務の流れは [シナリオテスト](scenario-test.md) で確かめ、粒度で区別する |
| 設計の方式 | ブラックボックス。内部の構造ではなく、`specification.md` の業務ルール・画面操作・状態・データの制約・入出力・エラーから、入力と期待結果を決める |
| 結合相手 | 下の「結合の範囲」に従い、システムの境界の内側では Mock・Stub を使わず、本物を結合する |
| 書く時期 | 基本は実装の後。期待結果は設計文書から決め、実装の動きを見て決めない |
| カバレッジ | 測定の対象。[ユニットテスト](unit-test.md) とあわせて測る（シナリオテストは含めない）。基準は `tests.md` の「品質ゲートと基準」に従う |

## 結合の範囲

- **システムの境界の内側は本物を使う**: 自分たちのモジュール・パッケージ・クラス、データベース、ファイルは、テストダブルで置き換えずに結合する。データベースやファイルは、テスト用に用意した本物（テスト用のデータベース、一時ディレクトリなど）を使う。
- **境界の外は提供元のテスト環境を使う**: 決済 API や外部の Web サービスなど、システムの外にあるものは、提供元のテスト環境（サンドボックスなど）があればそれを使う。
- **テスト環境が無い外部は代替を使う**: 提供元のテスト環境が無い外部は、テストダブルで置き換えてよい。その場合は、置き換えた外部とその範囲を PR本文の「動作確認」の未確認に書き、検証の限界を `tests.md` の「重点リスクと検証限界」に残す必要があれば `SKILL.md` の手順6に従う。
- **テスト環境はあるが作業環境に資格情報が無い外部は代替で進め、要否を確認する**: 提供元のテスト環境があっても作業環境にその資格情報が無ければ、作業を止めずにその外部をテストダブルで置き換えたテストを書いて検証できる範囲を進め、テスト環境で確かめられなかった範囲と理由（作業環境に資格情報が無いこと）を PR本文の「動作確認」の未確認に書く。外部サービスと接続したテストが必要かどうかは利用者が判断するため、`tests.md` の「テスト環境と外部境界」や利用者の指示で要否・実行方針がまだ決まっていなければ、`SKILL.md` の「判断待ちがある場合」に従って PR コメントで利用者に要否を確認する（必要なら資格情報の提供や、資格情報がある環境（CI のシークレットなど）でだけ実行する方針を `tests.md` に残すかもあわせて確認する）。すでに方針が決まっている場合は判断待ちにせず進め、検証方針や限界を `tests.md` に残す必要があれば `SKILL.md` の手順6に従って PR コメントに「設計文書に残す候補」として書く。

境界の内側をテストダブルで置き換えると、結合したときに起きる不具合（呼び出し方の食い違い、データの受け渡し、トランザクションなど）を見落とすため、内側では使わない。

## 書き方

- **ケースは設計文書から決める**: 業務ルールの表の行は、テストのデータとしてそのまま写す。画面操作・状態遷移・入出力・エラーは、`specification.md` に書かれた条件と結果をケースにする。設計文書に無いケースを、実装の動きを見て足さない。
- **実装の後に書く理由と注意**: 結合する部品がそろってから書くため、基本は実装の後になる。期待結果は凍結された設計文書から決まっているので、実装の後に書いても期待結果を実装に合わせない。テストが失敗したら、設計文書を正としてコードを直す（`SKILL.md` の手順5）。
- **失敗することも確かめる**: 書いたテストが本当に不具合を検出できるかを、期待結果を一時的に変えて失敗させるなどの方法で一度確かめる。最初から通るテストは、何も検出できないテストになっていることがあるため。
- **仕様として読めるように書く**: テストは設計文書と同じ言葉で書く（リポジトリにテスト名の言語の規約があればそれに従う）。`specification.md` の節や規則の名前でグループにまとめ、業務ルールの表のどの行かが分かる名前を付けて、人が設計文書と見比べられるようにする。

## 場面ごとの扱い

- **バグ修正**: 不具合が `specification.md` のどの記述を破っているかを示すインテグレーションテストを足す。実装の前に書ける場合（結合する部品がすでにそろっている場合）は、先に書いて失敗することを確かめてから直す。
- **結合テストを実行する仕組みが無い場合**: テスト用のデータベースが用意できないなど、実行する仕組みがプロジェクトに無い場合も、黙ってユニットテストだけで済ませない。`SKILL.md` の手順3の扱いに従う。
