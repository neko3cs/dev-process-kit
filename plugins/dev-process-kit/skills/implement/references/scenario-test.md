# 参考資料: シナリオテスト

`SKILL.md` の「実装する」の手順3で、シナリオテストを書くときに読む。

## 定義

| 項目 | 内容 |
| :--- | :--- |
| 呼び方 | 総合テスト（JSTQB のシステムテスト）に当たる |
| 確かめる設計 | `requirements.md` の業務要件（人とシステムで回す業務の流れ） |
| 対象 | 業務の流れ（シナリオ）に沿って、システム・アプリ全体が業務を回せるか。機能をまたぐ。1つの機能の振る舞いは [インテグレーションテスト](integration-test.md) で確かめ、粒度で区別する |
| 設計の方式 | 業務要件で決めた、システムが想定する業務の手順を、そのままテストの手順にする |
| 結合相手 | 本物の構成で動かす。システムの境界の外の扱いは [インテグレーションテストの結合の範囲](integration-test.md#結合の範囲) と同じ |
| 書く時期 | 基本は実装の後。業務の手順がそのままテストの手順になるので、先に書いてもよい |
| カバレッジ | 測定の対象にしない |

業務の手順がテストの手順になるため、業務要件そのものが間違っていなければ、実装の後に書いても間違ったテストにはなりにくい。

カバレッジを測らないのは、シナリオテストが業務要件のシナリオそのものだからである。コードカバレッジを上げるためにテストの手順を変えると、テストと業務要件を突き合わせられなくなる。カバレッジが足りない箇所は、ユニットテストとインテグレーションテストで補い、シナリオテストの手順は業務要件から変えない。

## 受け入れテストとの違い

シナリオテストは、業務の流れのうちシステムが担う部分を、テストコードで自動で確かめる。業務の手順にある人の作業（画面の操作、ファイルの投入など）は、テストコードの中で人の操作として再現する。

人を含む業務全体が回るかを確かめ、GO / NO-GO を判断するのは受け入れテストで、人が行う（`SKILL.md` の手順3）。シナリオテストが通っても、受け入れテストを済ませたことにはしない。

## 書き方

- **手順は業務要件から取る**: `requirements.md` の業務要件と利用シナリオに書かれた業務の手順を、順番どおりにテストの手順にする。各手順の後に、業務要件と受け入れ基準から決まる結果を確かめる。業務要件に無い手順を、実装の動きを見て足さない。
- **実装の手段はシステムの形で選ぶ**:
  - GUI アプリ: 画面を操作する UI テストとして書く。
  - バッチ: 処理を実行するテスト用のスクリプトを書き、出力や保存された結果をアサーションで確かめる。
  - 具体的なツールは、プロジェクトの既存のテストと規約に合わせる。
- **失敗することも確かめる**: 書いたテストが本当に不具合を検出できるかを、期待結果を一時的に変えて失敗させるなどの方法で一度確かめる。
- **仕様として読めるように書く**: テストは設計文書と同じ言葉で書く（リポジトリにテスト名の言語の規約があればそれに従う）。業務要件の名前でテストをまとめ、手順が業務の手順と見比べられるようにする。

## 場面ごとの扱い

- **シナリオテストを実行する仕組みが無い場合**: UI テストの環境が無いなど、実行する仕組みがプロジェクトに無い場合も、黙って省かない。`SKILL.md` の手順3の扱いに従う。
- **業務要件が変わらない変更**: 作業範囲に `requirements.md` の業務要件が含まれない変更では、新しいシナリオテストは書かない。既存のシナリオテストは回帰テストとして流す。
