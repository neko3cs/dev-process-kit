# 参考資料: ユニットテスト

`SKILL.md` の「実装する」の手順3で、ユニットテストとプロダクトコードを書くときに読む。テスト駆動の手順の根拠は [講演の要約](tdd-bootcamp-2020-wada.md) にある。

## 定義

| 項目 | 内容 |
| :--- | :--- |
| 呼び方 | 単体テスト（JSTQB のコンポーネントテスト） |
| 確かめる設計 | 詳細設計。文書にしないため、ユニットテストが詳細設計の代わりになる |
| 対象 | クラス・関数など、1つの部品の振る舞い |
| 設計の方式 | ホワイトボックス。内部の構造（分岐、境界、状態）を知ったうえでケースを決める |
| 結合相手 | テストダブル（Mock・Stub など）で置き換えて切り離してよい |
| 書く時期 | プロダクトコードより先に書く（テスト駆動開発、TDD）。手順は下の「テスト駆動で進める」 |
| カバレッジ | 測定の対象。インテグレーションテストとあわせて測る（シナリオテストは含めない）。基準は `architecture.md` の「検証方針と重点リスク」に従う |

`SKILL.md` の手順3の対応で、画面・保存・外部連携を介さずに入力から結果が決まる計算規則を、業務ルールの表の行に対応づけたユニットテストで確かめる場合も、この手順で先に書く。その場合のケースは内部の構造ではなく表の行から決める。

## テスト駆動で進める

TDD は品質保証の手段ではなく、コードを綺麗に保ちながら安心して開発を進めるための設計手法として扱う。歩幅を小さく保ち、手戻りを防ぐ。

### TODO リストを作る

部品を書き始める前に、その部品に必要な振る舞いを「これが通れば満たす」と言える単位まで小さなテストケースに分解し、リストにする。

- 例（FizzBuzz）: 「1を渡すと"1"を返す」「3の倍数で"Fizz"を返す」「5の倍数で"Buzz"を返す」「15の倍数で"FizzBuzz"を返す」
- 最も簡単で、次のテストへの足がかりになるものから着手する。
- 作業中に新しいケースに気づいたら、その場でリストに足す。ただし、利用者から見える振る舞いで設計文書に無いもの（仕様の不足）に気づいたら、リストに足して決めずに `SKILL.md` の手順4に従う。

### 1項目ずつ Red → Green → Refactor を回す

リストから1項目だけを選び、次を順に行う。複数の項目を同時に進めない。

#### Red（失敗するテストを書く）

- まだ存在しないクラス・メソッドに対して、理想の使われ方（インターフェース）を思い描きながらテストを先に書く。
- テストを実行し、意図した理由で失敗することを確かめる。コンパイルエラー（ビルド失敗）も正当な Red。
- 想定と違う理由で失敗した、または誤って通ってしまった場合は、何も検出できないテストになっていないかを確かめてから次に進む。

#### Green（最短でテストを通す）

テストを通す実装は、状況に応じて次の3つから選ぶ。どれを選んでも、Green になるまでは他のことを考えず、最短で通すことを優先する。

1. **仮実装（Fake It）**: 期待値をハードコードして、すぐに Green にする（例: `return "1";`）。正しさや美しさは後回しにする。
2. **明白な実装（Obvious Implementation）**: 実装が自明で確信がある場合は、最初から正しいコードを書く。
3. **三角測量（Triangulation）**: 一般化の方向に確信が持てない場合は、もう1つテストケース（リストの次の項目）を足し、2つの具体例から一般化を導く。

確信が持てなければ、明白な実装ではなく仮実装か三角測量を選ぶ。

#### Refactor（テストを保ったまま綺麗にする）

- Green を保ったまま、重複の除去・一般化・命名の改善をする。
- 小さな変更ごとにテストを実行し、Green のままであることを確かめる。崩れたら直前の変更を見直す。
- プロダクトコードだけでなく、直前に書いたテストコードも整える。

サイクルを終えたら、リストの項目に印を付けて次の項目に進む。リストが空になるまで繰り返す。

## 仕様として読めるように書く

ユニットテストは詳細設計の代わりなので、実装を読まなくても部品の振る舞いが分かる「動く仕様書」として書く。Red を書く最初の時点から、次の構造で書く（肥大化してから直すのではない）。

- **テストの言葉**: 設計文書と同じ言葉で書く。日本語の設計文書なら日本語で書く。リポジトリにテスト名の言語の規約があれば、それに従う。
- **仕様の文脈でまとめる**: 関連するテストケースを言語・フレームワークのグループ化の仕組み（`describe`、`@Nested`、入れ子クラスなど）でまとめ、グループ名を振る舞いを表す自然文にする。
- **テストケース名**: 入力に対してどう振る舞うべきかを、期待結果まで含めた自然文にする（例: `describe("3の倍数のときは数の代わりにFizzに変換する", () => { it("3を渡すと文字列Fizzを返す", ...) })`）。
- テストが増えて読みにくくなったら、この構造に沿ってグループ分けと名前を直す。テストコードはプロダクトコードと同じか、それ以上に丁寧に保守する。

## 場面ごとの扱い

- **バグ修正**: 原因の部品が分かれば、まず不具合を再現する失敗するユニットテストを書いてから直す。不具合が仕様どおりに動かないことは、あわせて [インテグレーションテスト](integration-test.md) で確かめる。
- **レビュー指摘への対応**: 部品の振る舞いを変える指摘は、先にその振る舞いのテストを足すか直してから、プロダクトコードを直す。
- **テストで確かめる振る舞いが無い変更**: 設定ファイルや文書だけの変更、生成されたコードなどには、このサイクルを求めない。
