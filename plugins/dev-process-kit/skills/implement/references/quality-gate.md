# 参考資料: 品質ゲートと検証ガードレール

`SKILL.md` の「実装する」の手順7で品質ゲートを通すとき、および PR 本文の「動作確認」をまとめるときに読む。

## 1. 品質ゲートの決め方と進め方

- **正本は `tests.md`**: 対象スコープ、実行する検証、合否基準、終了条件は `tests.md`（「品質ゲートと基準」「終了条件」「テスト環境と外部境界」）・規約・指示に従う。実行コマンドや閾値の正本が設定ファイルや CI ワークフローにある場合はそれを優先する。
- **定めが無い場合**: リポジトリに既存の仕組みがありローカル実行できるテスト・ビルド・型チェック・リンターをすべて通す。仕組みが無い検証は新規導入せず「未確認」とし、必要なら PR コメントに `tests.md` への追記候補として提案する。
- **既存の失敗と新たな失敗を区別する**: 実装前に記録した元々の失敗は無視してよいが、今回の変更で新たに壊した失敗は直す。
- **環境・権限不足で進めないとき**: 原因と再開条件を記録して「未確認」とし、同じ失敗を無制限に繰り返さない。

## 2. 検証のガードレール

プロジェクトのツールや言語に関わらず、検証の信頼性を保つために次を守る。

- **未実行・測定不能を合格にしない**: 見落としを「問題なし」と誤認させないため、未実行の検証、キャッシュによる省略、空の解析 DB・抽出 0 件・DB 接続失敗などを合格や未検出として扱わない。
- **検査を緩めて合格させない**: 品質基準の形骸化を防ぐため、テストの無効化・スキップ、閾値の引き下げ、解析ルール・重大度ポリシーの緩和、根拠の無い除外追加で通さず原因を直す。
- **終了コードとレポートの実体を確認する**: 失敗の見逃しを防ぐため、パイプや `|| true` 等で終了コードを隠さず、解析ツールが終了コード 0 を返す場合も SARIF や診断ログの中身まで読む。
- **指標と検証種別をすり替えない**: 実績を正確に伝えるため、実測値には指標名を明記し（例: 行カバレッジをブランチカバレッジと書かない）、Lint・通常テストの成功をセキュリティ解析や依存監査の完了として扱わない。CI で実行予定というだけでは確認済みにせず、既存 CI の結果を使う場合は対象コミット SHA と成果物を確認する。

## 3. 結果の分類と報告

PR 本文の「動作確認」および終わりの報告では、検証ごとに次の4つを区別する。誤検出や承認済み例外は根拠と対象を記録し、「検出 0 件」とは書かない（重大度不明の検出や未解決の基準違反を残したまま合格にしない）。

| 分類 | 扱い | 記載すること |
| :--- | :--- | :--- |
| 確認済み | 実際に実行・結果確認まで終え、基準を満たした | 実行環境、コマンド、結果（実測値は指標名つき） |
| 失敗・基準未達 | 失敗したか、基準を満たさなかった | 失敗内容と原因（未解決のまま Ready for review にしない） |
| 対象外 | 非対応の言語・プラットフォームやスコープ外 | 対象外とした理由 |
| 未確認 | 適用可能だが環境・資格情報・権限不足等で実行できなかった | 実行できなかった理由と再開条件 |
