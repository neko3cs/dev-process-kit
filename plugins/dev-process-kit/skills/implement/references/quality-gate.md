# 参考資料: 品質ゲートと検証ガードレール

`SKILL.md` の「実装する」の手順7で品質ゲートを通すとき、および PR 本文の「動作確認」をまとめるときに読む。

## 1. 品質ゲートの決め方

- **正本は `tests.md`**: 対象スコープ、実行する検証（フォーマット・Lint・型チェック・ビルド・テスト・カバレッジ・ミューテーション・PBT・セキュリティ検証等）、合否基準、終了条件は `tests.md`（「品質ゲートと基準」「終了条件」「テスト環境と外部境界」）、リポジトリの規約、利用者の指示に従う。
- **既存設定を優先する**: 実行コマンドや閾値の正本がリポジトリ内の設定ファイル・パッケージスクリプト・CI ワークフローにある場合は、それを優先して実行する。
- **定めが無い場合**: `tests.md`・規約・指示に品質ゲートの定めが無い場合は、リポジトリに既存の仕組みがありローカル実行できるテスト・ビルド・型チェック・リンターをすべて通す。仕組みが無い検証は新規導入せず「未確認」として扱い、必要なら PR コメントに `tests.md` への追記候補として提案する。

## 2. 進め方

- 定められた順序（指定が無ければビルド・型チェック・Lint → 通常テスト → 追加検証・セキュリティ検証の順）で実行し、前段の失敗を解消してから次へ進む。
- 実装前に記録した既存の失敗と、今回の変更で新たに壊した失敗を区別する。新たな失敗は原因を調べて実装やテストを修正し、影響する検証を再実行する。
- 実行環境・権限・外部依存の不足で進めない場合は、原因と再開条件を記録して「未確認」とし、同じ失敗を無制限に繰り返さない。

## 3. 検証のガードレール

プロジェクトのツールや言語に関わらず、次の原則を守る。

- **未実行・測定不能を合格にしない**: 未実行の検証、キャッシュによるコンパイル省略、空の解析 DB、抽出 0 件の解析、DB 接続失敗や照合不能な依存監査などを「未検出」「合格」として扱わない。
- **合格のために基準を緩めない**: テストの無効化・スキップ、閾値の引き下げ、解析ルールや重大度ポリシーの緩和、根拠の無い除外追加で合格にしない。
- **終了コードとレポートを隠さない**: ログ整形のパイプや `|| true` などで失敗の終了コードを隠さない。解析ツールの終了コード 0 が処理成功のみを意味する場合は、SARIF・レポート・診断ログの中身まで読んで検出の有無を確かめる。
- **指標をすり替えない**: 行カバレッジや領域カバレッジをブランチカバレッジとして報告しない。実測値には指標名を明記する。シナリオテストはカバレッジ測定に含めない。
- **検証の種類を混同しない**: Lint・型チェック・通常テストの成功を、セキュリティ静的解析・Sanitizer・依存脆弱性監査の完了として扱わない。CI で実行予定というだけでは確認済みにしない（既存 CI の結果を使う場合は、対象コミット SHA・完了状態・成果物を確認し、コミットが変わったら古い成果物を使わない）。
- **承認済み例外の扱い**: 誤検出や承認済み例外は根拠と対象を残し、「検出 0 件」とは記載しない。重大度不明の検出や未解決の基準違反を残したまま合格にしない。

## 4. 結果の分類と報告

PR 本文の「動作確認」および終わりの報告では、検証ごとに次の4つを明確に区別する。

| 分類 | 扱い | 記載すること |
| :--- | :--- | :--- |
| 確認済み | 実際に実行・結果確認まで終え、基準を満たした | 実行環境、コマンド、結果（カバレッジ等の実測値は指標名つき） |
| 失敗・基準未達 | 失敗したか、基準を満たさなかった | 失敗内容と原因（未解決のまま Ready for review にしない） |
| 対象外 | 非対応の言語・プラットフォームやスコープ外 | 対象外とした理由 |
| 未確認 | 適用可能だが環境・資格情報・権限不足等で実行できなかった | 実行できなかった理由と再開条件 |
